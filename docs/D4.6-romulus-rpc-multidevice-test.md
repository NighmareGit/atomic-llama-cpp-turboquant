# D4.6: Romulus RPC Multi-Device Test (GRAPH_COMPUTE_ALL)

**Date:** 2026-07-11
**Branch:** Path-D-Gpipeline-Assembly-Line
**Base commit:** `2f78713ab` (Path-B-Event-Support-Pipeline-Plus)
**Hardware:** Client: AMD Radeon RX 7900 XTX (ROCm) | Server: NVIDIA GeForce RTX 3060 Ti (CUDA, docker RPC on 127.0.0.1:50051)

## Summary

D4.6 tested the D4.5 GRAPH_COMPUTE_ALL implementation (`--rpc-multidevice`) on Romulus dual-GPU. The initial D4.5 build produced a CUDA error during graph_compute. Root cause: the EVENT_RECORD server handler in `ggml-rpc.cpp` removed `wait_compute_idle()`, allowing the server command processing thread to proceed before the CUDA compute finished, causing device context corruption.

## Fix Applied

Re-added `server.wait_compute_idle()` to the `RPC_CMD_EVENT_RECORD` handler in `ggml-rpc.cpp` (line 3737). The removal was originally needed for the deferred EVENT_RECORD pattern (Path B), but the D4.5 client now uses blocking `send_rpc_cmd` for EVENT_RECORD, making the `wait_compute_idle()` safe to restore.

## Multi-Device Test Notes

The `GGML_RPC_MULTIDEVICE=1` path correctly falls through to the normal single-device path when `n_devices_on_endpoint == 1` (server has only one CUDA GPU). Proper multi-device testing of the `GRAPH_COMPUTE_ALL` path requires multiple GPUs on a single endpoint (e.g., `rpc-server -d CUDA0,CUDA1`).

**Telemetry now works on BOTH paths (D4.10 implementation):**

| Scenario | RPC path | Telemetry |
|----------|----------|-----------|
| 1 GPU on RPC server (this test: `-d CUDA0`) | `GRAPH_COMPUTE` (single-device) | **Yes** — telemetry collected and returned in response |
| 2+ GPUs on RPC server (`-d CUDA0,CUDA1`) | `GRAPH_COMPUTE_ALL` (multi-device) | **Yes** — telemetry collected and returned in response |

This means the Romulus setup (7900 XTX local + 3060 Ti RPC with `-d CUDA0`) **is fully profiled** via the single-device `GRAPH_COMPUTE` path — no multi-GPU RPC server is required for basic profiler operation. The gating condition `n_devices_on_endpoint > 1` only restricts the `GRAPH_COMPUTE_ALL` path (server-side multi-GPU scheduling), not telemetry itself.

## Root Cause Analysis

The CUDA error (`CUDA_ERROR_ILLEGAL_ADDRESS` in `cudaFuncGetAttributes`) occurred because:
1. D4.5 removed `wait_compute_idle()` from the `RPC_CMD_EVENT_RECORD` handler
2. This allowed the server command processing thread to send the EVENT_RECORD response and process subsequent commands while the compute worker thread's CUDA operations were still in-flight
3. The next command (typically ALLOC_BUFFER or FREE_BUFFER) could then corrupt the CUDA device context

## Files Changed

- `ggml/src/ggml-rpc/ggml-rpc.cpp`: Re-added `server.wait_compute_idle()` in `RPC_CMD_EVENT_RECORD` handler

### draft-mtp Self-Speculation

For Qwen3.x `*_MTP.gguf` models with built-in NextN/MTP head weights, `--spec-type draft-mtp` without `-md` creates a second `llama_context` over the already-loaded target model (`LLAMA_CONTEXT_TYPE_MTP`). No separate draft GGUF file is needed. The MTP context uses its own KV cache (~184 MiB for this model) and routes graph construction to the NextN draft builders.

**Server startup log excerpt (n_max=2 shown; n_max=16 only differs in that parameter):**

#### Server A/B: No Spec vs draft-mtp n_max=16 vs n_max=2 (128-token generation)

The optimal draft length (`--spec-draft-n-max`) balances the cost of computing draft tokens against the acceptance rate. Proposing too many draft tokens wastes compute on tokens that get rejected; proposing too few limits the speedup from verified speculation.

| Config | Gen t/s (avg of 3) | Draft proposed | Draft accepted | Acceptance rate | Decode calls | Tokens per decode |
|--------|-------------------|----------------|----------------|-----------------|-------------|-------------------|
| No speculative | **80.0 t/s** | -- | -- | -- | 128 | 1.00 |
| draft-mtp n_max=16 | **96.9 t/s** | 271 | 107 | 39.5% | 48 | 2.67 |
| draft-mtp n_max=2 | **113.2 t/s** | 97 | 78 | 80.0% | 50 | 2.56 |
| **n_max=2 vs no spec** | **+41.5%** | -- | -- | -- | -- | -- |
| **n_max=2 vs n_max=16** | **+16.8%** | -- | -- | -- | -- | -- |

With `n_max=16`, the draft model proposes up to 16 tokens per decode step, but only ~2.1 are accepted on average (39.5% acceptance). The remaining ~14 draft tokens are wasted compute. With `n_max=2`, the acceptance rate jumps to 80%, and the wasted-draft overhead nearly vanishes.

**Recommended:** `--spec-draft-n-max 2 --spec-draft-n-min 1` for Qwen3.5-9B-MTP self-speculation.

### Notes

- The `ROCm0` device does not support backend sampling op `TOP_K`, so MTP draft sampling falls back to CPU sampler (logged as warnings, non-fatal). This is a known gap in llama.cpp's HIP/ROCm backend (CUDA uses NVIDIA CUB for this op). The CPU fallback is correct and the performance impact on MTP draft top-10 sampling is negligible.
- **`--spec-draft-n-max 2` is strongly recommended** over `n_max=16`. With n_max=16 the acceptance rate is only 39.5% (~2.1/16 tokens accepted), wasting 14 tokens of compute per decode step. n_max=2 achieves 80% acceptance with minimal waste, yielding +16.8% higher throughput (113.2 vs 96.9 t/s).
- For proper multi-GPU multi-device RPC testing (n_devices > 1 on endpoint), a server with multiple GPUs on the same endpoint is still needed. A single `rpc-server -d CUDA0,CUDA1` qualifies — this is **not** about multiple separate RPC endpoints.

### Key Findings

1. **MoE scaling**: The 35B MoE model's PP throughput (4,027 t/s) nearly matches the 4B dense model (3,835 t/s) because only 8/256 experts activate per token -- effective compute per token is ~3B active params.
2. **CUDA graph reuse**: Confirmed working on RPC server across all 128 decode steps (graph id 472->600).
3. **Fused Gated Delta Net**: Enabled for both autoregressive and chunked modes in the 35B MoE (SSM hybrid architecture).
4. **Asymmetric split**: `30,70` tensor split fits 7.2 GB on the 3060 Ti (8 GB VRAM) and 14.2 GB on the 7900 XTX (24 GB VRAM).
5. **Static caching fix**: Removing static caches from `rpc_trace_lvl()`, `sched_trace_lvl()`, and `pipeline_trace_lvl()` fixed the 0-byte trace file issue across `--repeat N` runs.
