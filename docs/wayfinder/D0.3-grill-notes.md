## Q1: KV Write Overlap

### When does each split write to KV cache?

KV writes occur in the **gather split** (ROCm0, final split 5 in 5-GPU prod). The KV store operations are embedded in the graph compute -- specifically in the `ggml_op` graph nodes that write to K/V cache tensors within the gather subgraph. The RPC compute splits (0-4) produce activations only; they do not directly write KV cells.

The KV cache management operations (`seq_rm`, cell allocation, K/V tensor writes) are invoked from `llama-context.cpp` after the graph compute completes, during `process_ubatch()` and the subsequent cell management pipeline.

### Can split N+1 read KV while split N is still writing?

**No, not currently.** The serial dispatch loop (`ggml_backend_sched_compute_splits`, line 2300 of ggml-backend.cpp) runs:
```
for (int split_id = 0; split_id < n_splits; split_id++) { ... }
```
Each iteration blocks on `event_wait_slot` before dispatching the next split. This ensures split N+1 cannot start until split N's compute + event_record completes.

**For GPipe:** The question becomes can token T+1 read KV while token T is still writing. This is also blocked today by `pipeline_barrier` which waits for all backends' events from the previous token's copy slot.

### Synchronization points in compute_splits

1. `ggml_backend_sched_wait_copy_slot()` -- waits for the backend's event at current copy slot (line 2338)
2. `ggml_backend_sched_wait_producer()` -- waits for producer backend's event for RPC relay tensors (line 2458)
3. `ggml_backend_event_synchronize()` -- when event_wait interface not available (line 2411)
4. `ggml_backend_event_record()` -- signals completion of split compute (line 2720)
5. `pipeline_barrier` -- synchronizes across all backends before advancing copy slot (line 2958)

### pipeline_barrier interaction with KV writes

`pipeline_barrier` iterates over all backends and calls `event_synchronize` (or `event_wait` for non-blocking) on the new copy slot's events. This ensures all backends have completed their previous split's work before the new copy slot is used. The gather split's KV writes are guaranteed complete by `pipeline_barrier` because the gather split's event_record signals "graph compute done" which includes KV writes.

**Key insight:** The RPC server processes `RPC_CMD_EVENT_RECORD` by calling `wait_compute_idle()` before responding (line 3370 of ggml-rpc.cpp). This means the event response confirms compute is idle -- KV writes are committed. `event_synchronize` or `event_wait` on the client side then blocks until this response arrives.

## Q2: MoE Expert Routing

### How are MoE expert IDs determined per token?

Expert IDs come from the `src[2]` tensor of the `GGML_OP_MUL_MAT_ID` node -- this is the routing tensor produced by the router FFN. For each token, the router produces a set of expert indexes.

### When is the expert routing decision made?

The routing decision is made during `graph_compute_async` on the split that contains the router FFN (one of the RPC compute splits). After compute, the `ids` tensor is read back to host via `ggml_backend_tensor_get()` (line 2519 in ggml-backend.cpp).

### Can expert routing overlap with KV write?

No overlap needed -- expert routing is per-token and self-contained. Token T+1's routing uses its own MUL_MAT_ID with its own router output. There is no inter-token dependency. The expert weight copy for T+1 (based on T+1's routing) is independent from T's KV write.

### What happens if expert routing changes mid-pipeline?

"Mid-pipeline" means across tokens, which is normal -- each token has its own expert routing. This is already handled by the existing code: each token's graph compute produces its own `ids` tensor, and each split's copy loop reads the expert IDs independently. No ordering constraint change.

## Q3: MTP Coupling Constraints

### How does MTP consume h_prev from target?

MTP extracts the hidden state before the final output norm via the `t_h_nextn` tensor. After `graph_compute_async` completes, `ggml_backend_tensor_get_async()` reads `t_h_nextn` into `embd_nextn.data` (llama-context.cpp lines 1588-1595).

### What is the timing relationship between MTP draft and target verify?

MTP draft runs on a separate model context (`ctx_dft`) with its own `ggml_backend_sched`. Target verify runs on `ctx_tgt`. Draft preparation (`common_speculative_draft()`) happens via `llama_decode(ctx_dft, ...)` which has its own compute_splits cycle. The draft and target sched instances are independent.

### Can MTP draft stages overlap with layer pipeline stages?

**Yes.** The draft context has separate backends and sched. Draft decode for token k+1 can overlap with target decode for token k, as long as the target's `t_h_nextn` (which feeds the draft) has been consumed. This is the basis for GPipe mode A.

### Does h_idx correction affect pipeline ordering?

`h_idx` correction (shifting indices after MTP acceptance) happens in `common_speculative_accept()`. This is a post-hoc adjustment to the KV cache structure, not a pipeline ordering constraint. It does not change when splits can dispatch.

## Q4: GPipe Ordering Model

### What is the producer-consumer relationship between splits?

Today it's implicit in the serial dispatch loop. Split N produces tensors that split N+1 consumes, but the sched handles this via copy-slot buffering and `tensor_copy` between backends. The actual producer-consumer relationship is enforced by `event_wait_slot` (blocking) or `event_wait_producer` (for RPC relay).

### How do we signal "KV ready for next stage"?

Currently: `pipeline_barrier` + copy-slot advance. After all splits complete, the barrier signals that all backends are done, and the next token can start.

For GPipe: Use `event_record` from the gather split after KV write graph compute completes. The token T+1 dispatch waits on this event before starting.

### What ordering guarantees does the current RPC event model provide?

Strong ordering:
1. Client sends `RPC_CMD_EVENT_RECORD` (fire-and-forget with deferred response pending)
2. Server processes `RPC_CMD_EVENT_RECORD` by calling `wait_compute_idle()` -- blocks until compute queue is empty AND compute inflight == 0
3. Server sends response back
4. Client `event_wait` calls `rpc_finish_event_response()` which blocks on reading the response
5. This provides: all graph compute completed before event response is delivered

Note: `wait_compute_idle` is a STRONGER guarantee than needed for KV-only ordering (it waits for all compute, not just KV writes). This is acceptable but adds latency.

### Can we use event_record/event_wait for split-to-split signaling?

**Yes.** The API already exists and is used for copy-slot management within a single token's decode. The extension for GPipe is:
- Producer (gather split): `event_record` on gather backend after KV compute
- Consumer (embed split for T+1): `event_wait` on the same event before dispatching

This replaces the `pipeline_barrier` dependency for inter-token ordering. The existing code structure supports this with minimal changes -- the event infrastructure (`ggml_backend_event_record`, `ggml_backend_event_wait`, event creation at sched init) is already in place.
