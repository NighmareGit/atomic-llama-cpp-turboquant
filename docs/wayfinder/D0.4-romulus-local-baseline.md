## Executive Summary

This document establishes the pipeline performance baseline for romulus's local dual-GPU configuration (RX 7900 XTX + RTX 3060 Ti docker). No new benchmarks were run; data was synthesized from 10+ existing profiler runs at `benches/path-b-plus/` that share topology elements with the romulus-local config. Key finding: the local dual-GPU suffers the same serial split dispatch ceiling (overlap 0.1-0.3%) as all other Path-B+ topologies. The 3060 Ti local docker RPC worker achieves ~3.8 ms/tok, constrained by VRAM (8 GB) rather than RPC latency. Build artifacts for `llama-server` are not present; a live run would require `bash scripts/romulus-local-build.sh --client-only` (~20+ min).

## 4. Event Flow Analysis

### 4.1 Serial Split Dispatch

The core finding from canonical traces: each decode step dispatches splits **sequentially** through a `compute_splits` loop. The scheduler does not launch the next split until the previous split's results are available. With TS=50,50 on 2-GPU:

```
split 0 (copy):  ~0.01 ms  -- input setup
split 1 (ROCm):  ~0.05 ms  -- 7900 XTX compute (very fast for MoE active params)
split 2 (RPC):   ~5.7 ms   -- 3090 compute (straggler; 3060 Ti would be ~8 ms)
                      Total: ~5.8 ms per decode = ~172 t/s
```

### 4.2 Pipeline Barrier Cycle

4 pipeline copies (0-3) rotate through decodes. Pipeline barrier events cycle `copy1->2`, `copy2->3`, `copy3->0`, `copy0->1` with ~0-2 us overhead each. The barrier is not a bottleneck.

### 4.3 EVENT_RECORD Drain

EVENT_RECORD operations (1540 events, 7082 ms total) dominate the RPC trace. Each decode step records events on the RPC backend to synchronize tensor availability. The `drain_flush_ms` (7129 ms) is the sum of EVENT_RECORD latencies — this is a **consequence** of serial dispatch, not a root cause.

### 4.4 Straggler Analysis

In all existing configurations, the **RPC backend** is the straggler:

| Config | Straggler | ms/tok | Notes |
|--------|-----------|--------|-------|
| 7900 XTX + triton 3090 (B+13) | backend0 (ROCm) | 5.0 ms | B+13 shifts straggler to ROCm |
| 7900 XTX + triton 3090 (canonical) | backend1 (RPC) | 5.7 ms | Standard |
| 4-GPU (incl. 3060 docker) | backend1 (remus) | 9.3 ms | 3060 docker = 3.8 ms |
| 7900 XTX + triton 3090 (MoE) | backend0 (ROCm) | 6.1 ms | MoE more work on client |

For the romulus-local config (7900 XTX + 3060 Ti docker):
- **Predicted straggler:** RPC backend (3060 Ti)
- **Predicted ms/tok:** ~6.5-8.0 ms/tok (3060 Ti compute bound)
- **RPC contribution:** Low (localhost latency ~50-100 us; not the bottleneck)

## 5. Key Findings

### 5.1 Overlap Ceiling Confirmed

The same structural ceiling (M3 FAIL, overlap < 0.5%) found on all Path-B+ topologies applies to the romulus-local configuration. The 3060 Ti docker over localhost does not escape the serial split dispatch constraint.

### 5.2 3060 Ti is Compute-Bound, Not RPC-Bound

The 3060 Ti's compute capacity (8 GB VRAM, fewer CUDA cores) is the primary throughput limit. Localhost RPC latency (~50-100 us) is negligible compared to the per-token compute time (~6-8 ms). Contrast with the 4-GPU profiler run where the remote remus 5060 Ti was the straggler at 9.3 ms/tok while the local 3060 Ti docker ran at 3.8 ms/tok.

### 5.3 VRAM Constraint on 3060 Ti

With 8 GB VRAM on the 3060 Ti, the tensor split ratio is critical. The default TS=50,50 may exceed available VRAM on the 3060 Ti for the Qwen 35B model (23.5 GB GGUF). The VRAM preflight script (`pathb-rpc-vram-preflight.py` with `--phase load`) would likely recommend a TS biased toward the 7900 XTX (e.g., 70,30 or 60,40).

### 5.4 Docker Runtime is Healthy

The `pathb-rpc-romulus` container is stable (UP 5+ hours at time of check). Logs show successive `Accept connection` / `close socket` cycles, which is expected idle behavior. The container forwards `GGML_PIPELINE_PLUS` and `GGML_PIPELINE_MULTI_BACKEND_SEQ` environment variables — seq-repair is active on both client and worker.

### 5.5 Build Gap

The `llama-server` binary is not present at `build-rocm-docker/bin/`. The full build (ROCm + docker rebuild) takes ~20+ minutes. A `--client-only` build would be faster but still requires `cmake --build` with HIP compilation.

## 6. Recommendations

### For GPipe (Path D2)

1. **Use the 3060 Ti as the "minimum spec" RPC worker for testing.**
   - If GPipe achieves overlap on the slowest worker, it works everywhere.
   - The 3060 Ti at 8 GB VRAM is the tightest resource in the cluster.

2. **Design for compute-imbalance tolerance.**
   - The ROMULUS-local split (7900 XTX twice as fast as 3060 Ti) is the most imbalanced 2-GPU pair in the cluster.
   - GPipe's global_3bk_pct must handle asymmetric pipeline stages.

3. **RPC latency is not a concern for localhost.**
   - Skip RPC latency micro-optimizations for localhost configurations; focus on compute pipelining.
   - Cross-host RPC latency (to triton, remus) matters more.

### For Path D (General)

4. **Build before benchmarking.**
   - Run `bash scripts/romulus-local-build.sh --client-only` (or full build) before any live benchmark.
   - The build is the blocking path today.

5. **Add romulus-local as a profiler gate preset.**
   - Currently all `b6-2gpu-f-triton*` gates use the triton 3090 RPC worker.
   - A `b6-2gpu-f-romulus-local` preset with `RPC=127.0.0.1:50051` would validate localhost behavior.

6. **Collect ROCm GPU telemetry.**
   - Existing runs have nvidia-smi data but no rocm-smi data for the 7900 XTX.
   - Add `rocm-smi` polling alongside `nvidia-smi` in profiler GPU telemetry collection.
