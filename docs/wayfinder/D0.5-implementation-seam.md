## 1. Integration Points

### 1.1 `llama_context` Additions

#### `llama_gpipe_state` (new member in `llama_context`)

Proposed additions to `src/llama-context.h`, inserted in the `llama_context` struct definition:

```cpp
// GPipe client scheduler state (GGML_SCHED_GPIPE=1)
struct llama_gpipe_state {
    int  n_stages;            // Number of pipeline stages (2 for initial: compute + gather)
    int  cur_stage;           // Current stage index (0..n_stages-1)
    int  microbatch_size;     // Tokens in flight (MTP draft depth)
    bool enabled;             // GPipe mode active flag

    // Per-stage token tracking
    std::vector<llama_seq_id> stage_tokens;  // Tokens assigned to each stage

    // Stage duration tracking (optional, for tuning)
    int64_t stage_start_us[GGML_SCHED_MAX_SPLITS];
};
```

#### `gpipe_enabled()` helper

Static helper following the pattern of `llama_pipeline_plus_enabled()` (lines 37-41 of `src/llama-context.cpp`):

```cpp
static bool llama_gpipe_enabled() {
    static int v = -1;
    if (v < 0) {
        const char * e = getenv("GGML_SCHED_GPIPE");
        v = (e != nullptr && atoi(e) != 0) ? 1 : 0;
    }
    return v != 0;
}
```

#### `llama_decode_gpipe()` new entry point

New function alongside the existing `llama_decode()` and `llama_decode_mtp_*()` family (lines 4152-4215 of `src/llama-context.cpp`):

```cpp
// GPipe mode decode: dispatches a token into the pipeline,
// advancing through stages without blocking on full decode.
LLAMA_API int32_t llama_decode_gpipe(
        struct llama_context * ctx,

```

### 1.2 `ggml_backend_sched` Additions

#### `ggml_sched_gpipe_init(sched, n_stages)`

Initializes extra GPipe event arrays in the scheduler. Called in `llama_context::sched_reserve()` (line 474 of `src/llama-context.cpp`) after `ggml_backend_sched_new()` when `GGML_SCHED_GPIPE=1`.

Location: `ggml/src/ggml-backend.cpp` -- new function near `ggml_backend_sched_new()` (~line 2830).

```cpp
// Initialize GPipe-specific event state.

```

#### `ggml_sched_gpipe_advance(ctx)`

Advances the GPipe stage counter in `llama_gpipe_state`. Called at the end of each pipeline stage's work in `process_ubatch()`.

Location: `src/llama-context.cpp` -- new function.

```cpp
// Advance to the next GPipe stage.
// Returns the new stage index, or -1 if the pipeline is complete.
static int ggml_sched_gpipe_advance(llama_context * ctx);
```

#### `ggml_sched_gpipe_wait(split_id)`

Waits on a specific GPipe stage event. Used by the gather stage to wait for compute stage completion, and by the embed stage of T+1 to wait for the gather stage's KV-ready signal.

Location: `ggml/src/ggml-backend.cpp` -- new static function alongside the existing `ggml_backend_sched_wait_copy_slot()` (~line 1938).

```cpp
// Wait for a GPipe stage's completion event.
// The event was recorded by the producer stage.
// If split_id < 0, waits for ALL pending GPipe stages.
static void ggml_sched_gpipe_wait(ggml_backend_sched_t sched, int split_id);
```

## 3. Decode Flow Change

### 3.1 Entry Point Selection

The proposed decode flow:

```
llama_decode(ctx, batch)
  |
  +-- if (gpipe_enabled && ctx->gpipe.enabled)
  |     |
  |     +-- llama_decode_gpipe(ctx, batch, h_prev)
  |           |
  |           +-- if (cur_stage == 0):
  |           |     embed(T) + RPC compute(T)
  |           |     -> ggml_sched_gpipe_record(compute_done_event)
  |           |
  |           +-- if (cur_stage == 1):
  |           |     ggml_sched_gpipe_wait(compute_done_event)
  |           |     gather(T) + KV write
  |           |     -> ggml_sched_gpipe_record(kv_ready_event)
  |           |
  |           +-- ggml_sched_gpipe_advance(ctx)
  |
  +-- else
        |
        +-- llama_decode_classic()  [existing ctx->decode(batch)]
```

The gate insertion point in `llama_context::decode()`:

```cpp
// In llama_context::decode(), before the ubatch processing loop:
if (gpipe.enabled) {
    // dispatch into gpipe mode
    return llama_decode_gpipe_impl(this, batch_inp, h_prev_ptr);
}
// ... existing classic decode path continues
```

### 3.2 Stage State Machine

```
State 0: COMPUTE_PIPELINE
    embed(T) -> RPC0(T) -> RPC1(T) -> RPC2(T) -> RPC3(T)
    -> event_record(compute_done)
    -> transition to GATHER_KV_WRITE

State 1: GATHER_KV_WRITE
    event_wait(compute_done)
    gather(T) + KV write
    -> event_record(kv_ready)
    -> sample(T) -> T+1 known
    -> transition to RELEASE_NEXT

State 2: RELEASE_NEXT (back to COMPUTE_PIPELINE for T+1)
    event_wait(kv_ready) [for gather of previous token]
    embed(T+1) -> repeat from State 0
```

### 3.3 Non-blocking vs Semi-blocking Variants

| Variant | Behavior | Use Case |
|---------|----------|----------|
| **Non-blocking** | Returns immediately after dispatching token into stage 0. Caller must poll/wait for completion. | Tightly coupled MTP loop where API overlap hides latency. |
| **Semi-blocking** | Blocks until the token reaches the gather stage (KV write point). T+1 dispatch can proceed immediately. | General single-sequence decode with MTP draft. |

Semi-blocking is the recommended starting point for D2.1 implementation.

## 4. Scheduler Touch Points

### 4.1 `compute_splits()` Serial Loop

File: `ggml/src/ggml-backend.cpp`, line 2295.

The existing loop:
```cpp
for (int split_id = 0; split_id < sched->n_splits; split_id++) {
    // 1. wait_copy_slot() - blocks on previous token's event for this split backend
    // 2. graph_compute_async() - runs the subgraph
    // 3. event_record() - signals completion to next split
    // 4. prefetch gather RPC inputs (B+15)
}
```

**Proposed GPipe change:** GPipe mode does NOT modify this loop. Instead, it:
1. Adds an outer loop over pipeline stages
2. Between outer-loop iterations, calls `pipeline_barrier()` for copy-slot advance (existing)
3. Uses additional per-stage events for cross-token producer-consumer signaling

### 4.2 `pipeline_barrier()` -- Unchanged

File: `ggml/src/ggml-backend.cpp`, line 2958.

The existing `pipeline_barrier()` remains identical for GPipe OFF mode. For GPipe mode, it is still called to advance copy slots within a single token's compute, but cross-token synchronization uses additional GPipe events instead.

### 4.3 `n_copies` Interaction

Currently: `n_copies = pipeline_parallel ? GGML_SCHED_MAX_COPIES : 1` (line 2789).

For GPipe: `n_copies` remains at its current value (determined by `cparams.pipeline_parallel`). GPipe ADDITIONALLY creates:
- Per-stage events for cross-token signaling
- Stage tracking state in `llama_gpipe_state`

The existing copy-slot pipeline (n_copies=4 for Path-B+) and the GPipe stage pipeline (n_stages=2 for initial) are independent concepts that coexist:
- Copy slots manage intra-token buffer reuse across backends
- GPipe stages manage inter-token dispatch ordering

### 4.4 Event record/wait Calls

**Existing calls** (in `compute_splits`):
- `ggml_backend_event_record()` at line 2719: signals split done for copy-slot management
- `ggml_backend_event_wait()` in `wait_copy_slot()` at line 1942: blocks on previous copy's event

**Additional GPipe calls:**
- `ggml_sched_gpipe_event_record(compute_stage_event)`: after all RPC compute splits complete for token T
- `ggml_sched_gpipe_event_wait(compute_stage_event)`: before gather split begins for token T
- `ggml_sched_gpipe_event_record(kv_ready_event)`: after KV write in gather split completes for token T
- `ggml_sched_gpipe_event_wait(kv_ready_event)`: before embed split for token T+1 dispatches

## 5. KV Handoff Design

Based on ADR-0002 (GPipe KV Ordering Model):

### 5.1 Producer-Consumer Protocol

```
Token T:
  Stage 0 (compute): embed(T) + RPC0..3(T)
    -> event_record(compute_done[T])
  Stage 1 (gather): event_wait(compute_done[T]) -> gather(T) + KV write
    -> event_record(kv_ready[T])

Token T+1:
  Stage 0 (compute): event_wait(kv_ready[T]) -> embed(T+1) + RPC0..3(T+1)
    -> event_record(compute_done[T+1])
  Stage 1 (gather): event_wait(compute_done[T+1]) -> gather(T+1) + KV write
    -> event_record(kv_ready[T+1])
```

### 5.2 Release Conditions

| Release | Condition | Not Required |
|---------|-----------|-------------|
| Token T+1 Stage 0 (embed) start | KV write for T complete (event_wait(kv_ready[T])) | Logits for T, sampling for T, h_nextn extraction for T |
| Token T Stage 1 (gather) start | RPC compute for T complete (event_wait(compute_done[T])) | Embed start for T+1 |
| Token T+1 Stage 1 (gather) start | RPC compute for T+1 complete | KV write for T (already done) |

### 5.3 MTP Coupling

MTP draft context (`ctx_dft`) has its own scheduler and operates independently from target (`ctx_tgt`):
- `h_prev` (hidden state from target last layer) flows through `embd_nextn` (line 1588-1595 of `src/llama-context.cpp`)
- `h_prev` is readable after the target's gather split completes
- For GPipe mode A: draft decode for token k+1 overlaps with target decode for token k

### 5.4 Event Signaling Implementation

Reuse the existing `ggml_backend_event_record`/`ggml_backend_event_wait` API (documented in `ggml/include/ggml-backend.h` lines 126-128):

```cpp
GGML_API void ggml_backend_event_record(ggml_backend_event_t event, ggml_backend_t backend);
GGML_API void ggml_backend_event_wait(ggml_backend_t backend, ggml_backend_event_t event);
```

GPipe state adds:
```cpp
// Per-stage events
ggml_backend_event_t gpipe_events[GGML_SCHED_MAX_STAGES];
```

Created in `ggml_sched_gpipe_init()` and consumed in `ggml_sched_gpipe_wait()`.

- `rpc-patch/` scripts -- no changes (fork collateral)

### 6.3 Flag-Gated Compilation

```cpp
// In llama_context::decode() or llama_context constructor:
if (llama_gpipe_enabled() && cparams.pipeline_parallel) {
    gpipe.enabled = true;
    // allocate GPipe state, events

    gpipe.enabled = false;
    // GPipe state remains default-initialized, zero overhead
}
```

| Risk | Mitigation |
|------|-----------|
| `llama_context` struct changes | New `gpipe` member is optional; zero-cost when disabled. Template instantiation unaffected. |

## 7. Stage Assignment (from D0.2 Split Topology)

Based on D0.2 findings, the natural GPipe stage split for the 5-GPU production topology:

### Initial Stage Split (2-stage pipeline)

```
Stage 0: embed(T) + RPC compute (remus 5060 + romulus 3060 + triton 3090 + triton 3070)
Stage 1: gather(T) + KV write + sample(T) (ROCm0 7900 XTX)
```

### Overlap Pattern

```
Token T:   [Stage 0: RPC compute ....................] [Stage 1: gather+KV+sample]
Token T+1:                                                 [Stage 0: RPC compute ...........]
```

### Cycle Time Estimate

From D0.2 section 4.3:
- Stage 0 (RPC compute): ~16.8 ms/tok effective (serial dispatch dominates, not raw compute)
- Stage 1 (gather): ~0.03 ms/tok (ROCm native, fast)

With GPipe overlap, the theoretical cycle time is:
- max(Stage0(T+1), Stage1(T)) = max(~16.8 ms, ~0.03 ms) = ~16.8 ms/tok

This does NOT improve throughput per token until Stage 0 is also split into sub-stages (finer-grained pipeline). The primary benefit is enabling `global_3bk_pct` > 1% by decoupling T+1's Dispatch from T's gather.

For actual throughput gain, a deeper pipeline (n_stages > 2) would be needed, potentially splitting the RPC compute chain into sub-pipelines per GPU.

## 8. Straggler Considerations

From D0.2 section 4.3:
- RPC1 (romulus 3060 docker) is the consistent straggler at ~2.1-4.0 ms/tok
- GPipe amplifies straggler impact: slow Stage 0 on 3060 blocks the entire pipeline release chain

Mitigation strategies:
1. **Finer sub-stages:** Split Stage 0 into per-backend sub-stages, allowing faster backends to start T+1 while the straggler finishes T
2. **Load-aware scheduling:** Give the straggler fewer layers (already done via TS balancing)
3. **Timeout + fallback:** If a stage stalls beyond p99 RTT (71.55ms), dispatch T+1 speculatively and reconcile

## 9. Domain Language Additions

| Term | Definition |
|------|------------|
| **GPipe stage** | A logical phase in the pipeline (e.g., "compute" or "gather") that processes one token and can run concurrently with other stages processing other tokens. |
| **Stage event** | An `ggml_backend_event_t` used for producer-consumer signaling between GPipe stages across tokens. |
| **Stage decoupling** | The separation of dispatch ordering from completion ordering via per-stage events rather than serial loop ordering. |
| **Microbatch depth** | The number of tokens concurrently in-flight in the GPipe pipeline, typically matching the MTP draft depth. |
