## Summary

Completed the GPipe stage state machine in `llama_decode_gpipe_impl()`. The skeleton previously only recorded/waited on events without dispatching any graph work. The implementation now dispatches the compute graph in Stage 0 and the gather graph in Stage 1, with proper event signaling between stages.

## Changes

### `src/llama-context.cpp` -- `llama_decode_gpipe_impl()`

**Stage 0 (compute):**
- Added graph dispatch via `ggml_backend_sched_graph_compute_async(sched, gf)` using the graph from `ctx->gf_res_prev->get_gf()`
- Null check on graph pointer to handle uninitialized state
- Event record (`ggml_sched_gpipe_record(sched, 0)`) signals compute_done
- Stage advances: `cur_stage = 1`

**Stage 1 (gather):**
- Event wait (`ggml_sched_gpipe_wait(sched, 0)`) blocks until Stage 0's compute_done
- Added graph dispatch via `ggml_backend_sched_graph_compute_async(sched, gf)` using the graph from `ctx->gf_res_prev->get_gf()`
- Event record (`ggml_sched_gpipe_record(sched, 1)`) signals kv_ready
- Stage advances: `cur_stage = 0`

## Design Decisions

1. **Graph source:** Uses `ctx->gf_res_prev->get_gf()` for both stages. This reuses the existing graph infrastructure. In D2.x, separate graphs for compute vs gather stages will be built and allocated.

2. **Null check:** The `if (gf)` guard handles the case where `sched_reserve()` has not yet built a graph. This makes the function safe to call before the first `decode()` invocation.

3. **Event signaling:** Follows the producer-consumer protocol from ADR-0002:
   - Stage 0 produces `compute_done` (event 0)
   - Stage 1 consumes `compute_done` and produces `kv_ready` (event 1)
   - Next token's Stage 0 will consume `kv_ready`
