## 4. Existing C1 Data Context

### 4.1 What rpc-path-c-tracking.md Shows

From Phase 5 traces (cross-host, client on romulus):

| Run | Topology | Endpoints | Splits | G (t/s) | Role |
|-----|----------|-----------|--------|---------|------|
| trace-f-3gpu-plus | 5070 + 5060 + 6600 | :50051 + :50052 | 4 | 42.8 | Path C "before" (client serializes) |
| trace-f-2gpu-plus | 5070 + 5060 | :50051 only | 3 | 48.9 | Ops workaround (not Path C) |

These are **cross-host** configs where each GPU is a separate machine. The client
serializes hops: each split waits for the previous RPC to complete before dispatching
the next. RTT count is high (7-22 per token) because each split incurs network round-trips.

### 4.2 How Triton Baseline Differs

| Dimension | Existing C1 (trace-f-*) | Triton D4.1 |
|-----------|------------------------|-------------|
| GPU locations | Cross-host (3 separate machines) | Co-located (same host, PCIe) |
| GPUs | 5070, 5060, 6600 (all mid-range) | 3090 (fast, 24GB) + 3070 (mid, 8GB) |
| RPC latency | ~350 us median (LAN) | ~50-100 us (loopback/local PCIe) |
| Client | romulus 7900 | romulus 7900 |
| Expected splits | 3-4 | 4 (embed + 2 RPC + gather) |
| Expected RTT/tok | 7-22 | ~8-12 (2 devices, fewer hops) |

### 4.3 What to Expect

Based on D0.2 topology map and D0.4 baseline extrapolation:

- **Splits per decode**: 4 (embed + RPC0 + RPC1 + gather)
- **Straggler**: triton 3070 (8GB VRAM cap, fewer CUDA cores than 3090)
- **3090 util**: 40-70% (fast GPU, may idle waiting for 3070)
- **3070 util**: 70-95% (compute-bound, VRAM-capped)
- **RPC RTT contribution**: Low (~50-100 us median, PCIe loopback)
- **overlap_pct**: < 1% expected (same serial dispatch ceiling as all Path-B+)
- **global_3bk_pct**: < 1% expected (no cross-token overlap without GPipe)

The key insight for Path C: server-side scheduling would let the 3090 and 3070
execute concurrently via local CUDA events instead of sequential client-driven splits.
Target: 2x server GPU duty cycle (both GPUs busy simultaneously).
