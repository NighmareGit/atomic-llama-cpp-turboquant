# D4.1 — Romulus Dual-GPU Baseline Analysis

**Date:** 2026-07-11  
**Hardware:** AMD Radeon RX 7900 XTX (24 GB, PCIe 4.0 x16) + NVIDIA RTX 3060 Ti (8 GB, PCIe 1.0 x4 via docker RPC)  
**CPU:** Intel Core i7-14700K (28 threads, 80 GB RAM)  
**Software:** llama.cpp `eb1e5a261` (Path-D-Gpipeline-Assembly-Line branch), ROCm 7.2.3, CUDA 12.8  
**RPC Protocol:** v4.4 — `peer_copy=yes dual=no`  

---

## Summary

This baseline measures dual-GPU throughput, per-device RPC splits, and trace telemetry
for three model architectures on the romulus local setup (7900 XTX client + 3060 Ti
RPC) **before** enabling GRAPH_COMPUTE_ALL (D4.5).

## 2. Server API Measurements

Measured via llama-server API with `--no-warmup`.

### 2.1 Multi-turn Conversation (9B MTP, ctx=16K)

| Turn | Context | Prompt Tokens | Gen Tokens | pp (t/s) | tg (t/s) |
|:----:|:-------:|:-------------:|:----------:|:--------:|:--------:|
| 1 | Mars colony challenges | 38 | 128 | 138.6 | 60.2 |
| 2 | Power system follow-up | 157 | 21 | 1,101.5 | 68.5 |
| 3 | Computing infra follow-up | 187 | 128 | 1,297.6 | 59.6 |

**Observation:** Prompt processing speeds up dramatically (138 -> 1,298 t/s) as
KV-cached context grows, demonstrating effective prompt caching. Generation remains
stable at 59-69 t/s regardless of context depth. Token truncation on turn 2 suggests
EOS token sensitivity.

### 2.2 Reasoning Benchmarks (9B MTP, ctx=16K)

| Test | Prompt Tokens | Gen Tokens | pp (t/s) | tg (t/s) | Finish |
|:----|:-------------:|:----------:|:--------:|:--------:|:------:|
| Calculus (displacement/distance) | 91 | 7 | 885.3 | 75.0 | stop |
| Einstein's Riddle (logic puzzle) | 212 | 19 | 1,018.5 | 67.4 | stop |
| 12 Coins Puzzle (abstract reasoning) | 80 | 512 | 810.2 | 59.5 | length |
| Quantum computing (multi-turn) | 22->142 | 128 ea | 272-1,123 | 58-61 | length |

**Observation:** Reasoning tasks hit early stop tokens (stop) on complex multi-step
problems, suggesting the model terminates reasoning prematurely. The 12-coin puzzle
was the only task to fully utilize max_tokens=512.

**Note:** Output quality was degraded for MTP models run without `--spec-type draft-mtp`
(due to RPC OOM with dual context). This affects content correctness but not timing
measurements.

## 4. Per-Device Tensor Split

### 4.1 VRAM Allocation

| Device | Total VRAM | Free (idle) | Budget (load) |
|--------|:----------:|:-----------:|:-------------:|
| **RPC0** (3060 Ti, docker) | 8,192 MiB | 7,825 MiB | ~4.26 GB |
| **ROCm0** (7900 XTX, native) | 25,760 MiB | 24,312 MiB | ~20.36 GB |

### 4.2 Tensor Split Impact

The VRAM preflight determined optimal tensor splits:

**9B MTP and Llama 8B** (5.5 GiB models):
```
ts=45,55 -> RPC: ~2.5 GiB weights + ~2.6 GiB KV cache = ~5.1 GiB (fits in 8 GB)
             ROCm: ~3.0 GiB weights + ~2.6 GiB KV cache = ~5.6 GiB (fits in 24 GB)
```

**35B APEX MTP** (21.86 GiB MoE model):
```
ts=25,75 -> RPC: ~5.5 GiB weights + ~0.5 GiB KV cache = ~6.0 GiB (fits in 8 GB)
             ROCm: ~16.4 GiB weights + ~1.5 GiB KV cache = ~17.9 GiB (fits in 24 GB)
```

### 4.3 RPC Throughput Impact

The `ts=45,55` split puts 45% of layers on the 3060 Ti (PCIe 1.0 x4 chipset-attached
via docker). RPC latency adds approximately 10-15 ms per round-trip to TG latency,
which is the dominant factor in the 16 ms/token generation time.

## 6. Key Findings

### Finding 1: PP scales well across both GPUs

With dual GPU (ROCm,RPC), prompt processing achieves:
- 9B models: **2,190-2,666 t/s** (pp512) -- near theoretical peak for the architecture
- 35B MoE: lower due to model size and token split inefficiency

For comparison, a single RPC-only (3060 Ti) benchmark gave only **115-511 t/s** for
the same model. The 7900 XTX contributes ~5x more PP throughput.

### Finding 2: TG is RPC-latency bound

Text generation is consistently **59-64 t/s** across all three models, suggesting
the bottleneck is RPC round-trip latency (not model size). Each TG step requires:
1. Forward pass on ROCm0 (7900 XTX) -- ~4 ms
2. Forward pass on RPC0 (3060 Ti) -- ~8 ms
3. Synchronization + data transfer -- ~4 ms

Total: ~16 ms/token = 62.5 t/s, matching empirical measurements.

### Finding 3: RPC protocol v4.4 limits dual-GPU efficiency

The RPC connection reports `dual=no`, indicating the current Path-B+ protocol
uses separate per-tensor graph_compute commands rather than the batched
GRAPH_COMPUTE_ALL approach (D4.5). This means each TG step generates:
- N tensor transfers (get_tensor/set_tensor) per backend
- Two round-trip graph_compute calls
- Multiple synchronization points

D4.5's GRAPH_COMPUTE_ALL should reduce this to a single server-side dispatch.

### Finding 4: Prompt caching dramatically improves PP throughput

The llama-server prompt cache shows:
- First turn: pp=138 t/s (cold cache, 38 tokens)
- Third turn: pp=1,298 t/s (warm cache, 187 tokens with 4 cached prompts)
- Cache size reached 417 MiB after 4 prompts

PP throughput improves ~9x as the KV cache accumulates.

### Finding 5: MTP models require `--spec-type draft-mpt` for correct output

MTP models (combined target+draft GGUF) generate garbled output when loaded without
MTP speculation enabled. However, enabling MTP (~spec-type draft-mtp) creates a
second llama_context on the RPC server, which causes CUDA OOM on the 8 GB 3060 Ti
for anything beyond small contexts. This is a known constraint.

### Finding 6: 35B APEX model fails in llama-bench but works in server

The Qwen3.6 35B APEX MTP model triggers an architecture support error in
llama-bench but loads and runs correctly in llama-server. This is a
llama-bench compatibility issue with the Qwen3.6 APEX variant.

### Finding 7: Tensor split 45/55 is optimal for 8-9B models

VRAM preflight confirms `ts=45,55` as the optimal split for sub-10B models:
- 3060 Ti gets 45% of layers (~2.5 GiB weights + KV cache)
- 7900 XTX gets 55% (~3.0 GiB weights + KV cache)
- Each device has ~1.5-2 GiB headroom for KV cache growth

For the 35B MoE model, `ts=25,75` is required to fit the 3060 Ti's 8 GB budget.

## 8. Recommendations for D4.5/D4.6

1. **GRAPH_COMPUTE_ALL should improve TG latency** by batching all tensor compute
   on the server side into a single RPC call, eliminating per-tensor round-trips.
   Baseline TG=62 t/s means ~16 ms/token. GRAPH_COMPUTE_ALL could reduce this to
   ~8-10 ms/token (closer to single-GPU TG on the 7900 XTX).

2. **Profile with GGML_SCHED_TRACE first, then RPC_TRACE.** The scheduler trace
   (21,535 lines) is 6x larger than the RPC trace (2,086 lines) for the same
   workload. Start with sched trace analysis and filter to RPC events.

3. **Test with non-MTP models for output quality comparison.** The MTP model
   generates garbled output without `--spec-type draft-mtp`. Use
   `Meta-Llama-3.1-8B-Instruct-Q5_K_M` for correctness validation.

4. **35B model requires `ts=25,75` for 8 GB RPC budget.** Any test with the
   APEX model must use this split or risk CUDA OOM on the 3060 Ti.
