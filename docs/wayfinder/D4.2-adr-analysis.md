## 1. Option Analysis

### Option A — Client-Driven (No Change)

| Dimension | Analysis |
|-----------|----------|
| **Mechanism** | Client `ggml_backend_sched` splits graph per-device; each triton GPU (`:50054` 3090, `:50055` 3070) is a separate RPC endpoint. Client serializes: `GRAPH_RECOMPUTE(3090)` -> `COPY_TENSOR` -> `GRAPH_RECOMPUTE(3070)`. |
| **Client impact** | None. Existing Path-B+ scheduler unchanged. |
| **Server impact** | None. `rpc-server` remains passive. |
| **RPC protocol** | No changes. Uses existing `GRAPH_RECOMPUTE`, `COPY_TENSOR`, `GET_TENSOR`. |
| **Backward compat** | Full. This is the baseline. |
| **Effort** | S (zero — already works) |
| **Risks** | 3070 sits idle while 3090 computes (5-6% load on 3070 vs 27-31% on 3090 per D0.2). Cross-device copy traverses client (`RPC_CMD_COPY_TENSOR` over network). Serial dispatch wastes ~2-4 ms/tok on triton-local overhead that could be PCIe-local. |

### Option B — Server-Side `GRAPH_COMPUTE_ALL`

| Dimension | Analysis |
|-----------|----------|
| **Mechanism** | Client sends ONE `GRAPH_COMPUTE_ALL` with full graph + device list `[3090, 3070]`. Server creates internal `ggml_backend_sched`, splits graph across its own GPUs, handles inter-device copy via PCIe P2P. Client receives single response. |
| **Client impact** | Moderate. Must detect same-endpoint devices, buffer splits, send combined graph. First RPC split sends `GRAPH_COMPUTE_ALL`; subsequent splits on same endpoint become no-ops. Output readback simplified to single `GET_TENSOR`. |
| **Server impact** | Large. New `create_multi_device_sched()` helper. New `stored_multi_graph` cache. New command handler for `RPC_CMD_GRAPH_COMPUTE_ALL` / `RPC_CMD_GRAPH_RECOMPUTE_ALL`. Must handle graph deserialization for full (non-split) graph. |
| **RPC protocol** | Add 2 commands: `RPC_CMD_GRAPH_COMPUTE_ALL` (18), `RPC_CMD_GRAPH_RECOMPUTE_ALL` (19). Request: `n_devices + device_ids + serialized_full_graph`. Response: `result + output_device`. Bump proto minor version or add capability flag (`RPC_CAP_MULTI_DEVICE`). |
| **Backward compat** | Good with fallback. Old client + new server: client sends per-device `GRAPH_COMPUTE`, server handles normally. New client + old server: client detects missing capability, falls back to per-device. |
| **Effort** | L (4 phases C2-C5 in plan: server sched, client combined submission, output retrieval, HELLO negotiation) |
| **Risks** | Server-side scheduler must allocate intermediate buffers (`ggml_backend_sched_reserve`). Graph serialization format must carry full graph, not per-device subgraph. `event_record`/`event_wait` interface must be non-NULL for RPC backends (known assert issue per plan red-team). Memory pressure on server doubles (both GPUs allocated simultaneously). |

### Option C — Server-Side Parallel Dispatch

| Dimension | Analysis |
|-----------|----------|
| **Mechanism** | Client still splits graph per-device (knows layer assignment), but sends `GRAPH_RECOMPUTE` to BOTH triton GPUs in parallel (overlapping network). Server dispatches each GPU's work concurrently using CUDA streams. Inter-device copy still goes through client (no server-local PCIe). |
| **Client impact** | Moderate. Must issue parallel `GRAPH_RECOMPUTE` sends (non-blocking sockets or async I/O). Must handle out-of-order responses. No graph format change. |
| **Server impact** | Moderate. Must support concurrent `GRAPH_RECOMPUTE` handlers (thread-per-connection or async event loop). Current `rpc-server` is single-threaded per connection; needs either per-device threads or `io_uring`/`epoll` async. |
| **RPC protocol** | No new commands. Uses existing `GRAPH_RECOMPUTE` but issued concurrently. May need `RPC_CMD_FLUSH` or barrier to synchronize. |
| **Backward compat** | Good. Old clients send serial; server handles. New clients send parallel; server handles. No wire-format change. |
| **Effort** | M (server threading/async refactor + client parallel send logic) |
| **Risks** | Server thread safety: current `rpc_server` is not thread-safe (shared `backends`, `stored_graphs`). Concurrent graph compute on same GPU would corrupt state. Must partition: one thread per device, not per connection. Inter-device copy still traverses client (no RTT savings on copy). Partial RTT reduction only — saves serial dispatch latency, not copy latency. |

## 2. What D4.1 Baseline Data is Needed

| Metric | Source | Informs | Why It Matters |
|--------|--------|---------|----------------|
| **Per-device RTT count** | C1 trace on triton dual-GPU | Option B vs C | Current RTTs per token for triton devices. Option B reduces from N to ~2 (one SET_TENSOR batch, one GRAPH_COMPUTE_ALL, one GET_TENSOR). Option C reduces only the serial dispatch overhead. |
| **3090 vs 3070 compute ms/tok** | C1 split timing | Option C slack | If 3090 takes 3.2 ms and 3070 takes 0.5 ms, parallel dispatch saves ~0.5 ms (3070 overlaps with tail of 3090). If gap is larger, more savings. |
| **COPY_TENSOR ms (3090->3070)** | C1 trace | Option B savings | Current cross-device copy goes through client (2 RTTs). Option B makes it PCIe-local (<<1 ms). Quantifies Option B's advantage. |
| **Server GPU utilization %** | `nvidia-smi` during decode | Option C feasibility | If 3090 is at 95% util, parallel dispatch has no slack. If at 60%, there's room for overlap. |
| **3070 VRAM usage** | C1 metadata | Option B memory pressure | `GRAPH_COMPUTE_ALL` requires both GPUs to hold intermediate buffers simultaneously. If 3070 is already near VRAM cap, combined allocation may OOM. |
| **Client-side split serialization overhead** | C1 trace (`input_wait_copy_ms`) | All options | Baseline for how much time is spent waiting vs computing. Sets the ceiling for improvement. |

## 3. Preliminary Assessment (from existing C1 data)

### What we know from `rpc-path-c-tracking.md`

| Data Point | Value | Implication |
|------------|-------|-------------|
| trace-f-3gpu-plus | 42.8 t/s, 4 splits (5070+5060+6600) | Multi-GPU RPC works but throughput limited by serial remus hops |
| trace-f-2gpu-plus | 48.9 t/s, 3 splits (5070+5060) | Dropping the 3rd GPU recovers 6 t/s — serial hop tax is real |
| Remus feasibility | 5060 (CUDA) + 6600 (ROCm) need C2 aggregation | Heterogeneous server-side sched is harder; triton 3090+3070 (both CUDA) is the easier spike |
| D0.2 split topology | 3090: 27-31% load, 3070: 5-6% load | 3070 is massively underutilized. Serial dispatch means 3070 idle for 70-80% of token time. |

### Inference

**Option B is most promising for these reasons:**

1. **RTT reduction is large and provable.** Current: 4+ RTTs for triton devices (SET_TENSOR, GRAPH_RECOMPUTE(3090), COPY_TENSOR out, COPY_TENSOR in, GRAPH_RECOMPUTE(3070), GET_TENSOR). Option B: 2 RTTs (SET_TENSOR_BATCH, GRAPH_COMPUTE_ALL, GET_TENSOR). That's 50%+ RTT reduction for triton-local traffic.

2. **Copy becomes PCIe-local.** The 3090->3070 hidden state copy currently traverses the client (romulus -> triton -> romulus -> triton). Option B keeps it on-triton (PCIe P2P, ~10-50 GB/s vs network ~1-10 GB/s).

3. **3070 underutilization is addressed.** Server-side scheduler can pipeline: 3090 computes layers N-1 while 3070 computes layers N (temporal overlap). Client cannot achieve this because it doesn't know server-internal timing.

4. **Alignment with D5.** If D5 (deeper pipelining) succeeds, the client will have more stages. Offloading triton's dual-GPU scheduling to the server simplifies the client scheduler's view (one endpoint, one split instead of two).

**Option C is less attractive:** Parallel dispatch saves only the serial dispatch latency (~0.5-2 ms), not the copy RTT. Server threading refactor is risky (thread safety in `rpc_server`).

**Option A is the fallback:** If D4.1 reveals 3070 VRAM pressure or server scheduler complexity is too high, we proceed to D5 with client-only pipelining.

## 4. Proposed Decision Timeline

### Minimum data needed from D4.1

| # | Data | Threshold for Option B |
|---|------|------------------------|
| 1 | 3070 VRAM headroom | >= 2GB free after model load (for intermediate buffers) |
| 2 | 3090->3070 COPY_TENSOR ms | >= 1 ms (justifies PCIe-local move) |
| 3 | Server GPU util (3090) | <= 90% (room for scheduler overhead) |
| 4 | RTT count per token (triton devices) | >= 3 (justifies GRAPH_COMPUTE_ALL) |

### Decision Rubric

| Condition | Best Option |
|-----------|-------------|
| 3070 VRAM headroom < 1GB | **A** (Option B would OOM) |
| COPY_TENSOR < 0.3 ms AND 3090 util > 95% | **A** (no savings, no slack) |
| COPY_TENSOR >= 1 ms AND 3070 VRAM OK AND server CUDA same-gen | **B** (maximum savings) |
| COPY_TENSOR < 1 ms AND 3090 util < 80% AND threading feasible | **C** (moderate savings, less code) |
| All thresholds met | **B** (default — highest ceiling) |

### Recommendation

Proceed with **Option B+ (`GRAPH_COMPUTE_ALL` + weighted weight placement)** as the default choice.

#### Critical Finding: Auto-Partition is Broken for Same-Type GPUs

`ggml_backend_sched_split_graph()` assigns nodes based on buffer-type affinity (ggml-backend.cpp:1160-1180). For two CUDA backends supporting identical ops:
- Backend 0 (3090) matches everything first
- Backend 1 (3070) never gets anything
- **Result: all work goes to 3090, 3070 stays idle**

The scheduler only assigns to 3070 if weight tensors are pre-allocated on it via SET_TENSOR. The "reuse auto-partition" simplicity choice produces an equal 50/50 split where the 3070 (1.75x slower) becomes the bottleneck.

[Performance audit](D4-performance-audit.md) confirms:
- Equal split: 30 layers each → 3070 at 4.2 ms (bottleneck) → 222 t/s
- Weighted split (64/36): 38 on 3090, 22 on 3070 → balanced at 3.08 ms → 296 t/s
- **Uplift: +33%** (11x the 3% threshold)

#### Revised Option B+ Specification

| Element | Original (Option B) | Revised (Option B+) |
|---------|--------------------|---------------------|
| Partition method | Reuse auto-partition (backend_from_buffer) | Client-driven weighted weight placement |
| Weight assignment | Even 50/50 | Proportional to GPU speed ratio |
| Speed detection | None | Benchmark or capability handshake |
| Server code changes | Full server-side scheduler | Same (minimal — scheduler just follows weights) |
| Client code changes | GRAPH_COMPUTE_ALL submission | + weighted layer assignment during SET_TENSOR |

#### Decision Rubric (Updated)

| Condition | Best Option |
|-----------|-------------|
| Single server GPU | **A** (per-device RPC, no Path C benefit) |
| 2+ GPUs, same type | **B+** (GRAPH_COMPUTE_ALL + weighted weight placement) |
| 2+ GPUs, different types | **B** (GRAPH_COMPUTE_ALL, partition by backend type) |
| VRAM pressure on any GPU | Fallback to **A** with documentation |
| All thresholds met | **B+** (default — highest ceiling) |

#### Contingency

Contingent on D4.1 confirming:
- 3070 has >= 2GB VRAM headroom (for additional layers)
- CUDA P2P enabled (for fast cross-device copy)

If P2P fails, cross-device copy doubles (~600 us) and uplift drops to ~18% — still well above 3%.
