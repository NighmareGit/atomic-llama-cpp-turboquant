# D4.4 Codebase Analysis: Server-Side RPC Infrastructure for GRAPH_COMPUTE_ALL

## 1. Current Server Architecture

### Thread Model
- **Accept thread**: `ggml_backend_rpc_start_server()` (line 3410) blocks on `server_socket->accept()` in a loop.
- **Per-client connection thread**: Each accepted socket spawns a detached `std::thread` running `rpc_connection_thread()` (line 2961). This thread:
  1. Reads the first byte (HELLO or CHANNEL_BIND).
  2. Delegates to `rpc_serve_client()` (line 3004) for the main command loop.
- **Compute worker thread**: Inside each `rpc_server` instance, a single `std::thread` runs `compute_worker_loop()` (line 2901). This serializes all graph compute jobs via a `std::deque<std::function<void()>>` queue.

Result: **1 connection thread + 1 compute worker thread per client**. The connection thread handles all non-compute commands inline; compute commands are enqueued.

### Command Dispatch Flow
`rpc_serve_client()` (line 3004):
1. Reads 1-byte command from socket (`cmd`).
2. Validates `cmd < RPC_CMD_COUNT` (line 3098).
3. Dispatches via a large `switch (cmd)` statement (lines 3101-3401).
4. Most handlers call `recv_msg()` for input, invoke a `rpc_server` method, then `send_response()`.
5. Compute commands (`RPC_CMD_GRAPH_COMPUTE`, `RPC_CMD_GRAPH_RECOMPUTE`) call `server.enqueue_graph_compute()` / `server.enqueue_graph_recompute()` — fire-and-forget, no response sent.

### How `rpc_backend_graph_compute` Works End-to-End
Client-side `ggml_backend_rpc_graph_compute()` (line 2089):
1. Checks graph UID cache (`rpc_dev_ctx->last_graph_uid`).
2. If cached: sends `RPC_CMD_GRAPH_RECOMPUTE` with `{device}` (4-byte request). No response expected.
3. If new: calls `serialize_graph()` (line 2062) which packs `| device | n_nodes | nodes | n_tensors | tensors |` into a byte buffer, then sends `RPC_CMD_GRAPH_COMPUTE`.
4. Both paths are fire-and-forget (no server response). The client later sends `RPC_CMD_EVENT_RECORD` for pipeline barrier ordering.

Server-side:
1. `rpc_server::enqueue_graph_compute()` (line 2923) wraps `graph_compute()` in a lambda and submits to `compute_queue`.
2. `compute_worker_loop()` dequeues and executes.
3. `rpc_server::graph_compute()` (line 2785) deserializes the graph and calls `ggml_backend_graph_compute(backends[device], graph)` — **single backend, no scheduler**.

## 2. Current Split/Device Model

### Multi-GPU Management
- `ggml_backend_rpc_start_server()` (line 3410) takes `n_devices` + `devices[]` (from `-d CUDA0,CUDA1`).
- Each device is initialized via `ggml_backend_dev_init()` and pushed into a `std::vector<ggml_backend_t> backends`.
- This vector is copied into each `rpc_server` instance (line 2234, stored as `backends`).
- `stored_graphs` is a `std::vector<stored_graph>` sized to `backends.size()` — one cached graph per device.

### Per-Command Device Assignment
- Each `rpc_msg_graph_recompute_req` carries a `uint32_t device` field (line 648).
- `graph_compute()` deserializes the device from the input buffer (line 2792) and validates `device < backends.size()`.
- Each device's graph is computed and cached independently. The server has **no concept of cross-device graph splitting**.

### No Server-Side Scheduler
There is **zero** use of `ggml_backend_sched` server-side. Each GPU runs its graph in isolation. Cross-device tensor copies are driven by the client via `RPC_CMD_COPY_TENSOR` / `RPC_CMD_COPY_TENSOR_PEER` (lines 3270, 3282).

## 3. Graph Compute Analysis

### GRAPH_COMPUTE Flow
1. Client serializes the full subgraph for one device (operations + tensor shapes, no allocated buffers).
2. Server deserializes into a fresh `ggml_cgraph` using `ggml_new_graph_custom()` (line 2823) into a pre-allocated `stored_graphs[device].buffer`.
3. `ggml_backend_graph_compute(backends[device], graph)` runs synchronously on the compute worker thread.
4. Result: graph is cached in `stored_graphs[device].graph` for future recompute.

### GRAPH_RECOMPUTE Flow
1. Client sends `RPC_CMD_GRAPH_RECOMPUTE` with `{device}` (4 bytes).
2. Server retrieves `stored_graphs[device].graph` and calls `ggml_backend_graph_compute()` again (line 2870).
3. No serialization/deserialization overhead.

### Where the Server Blocks on Compute
- `ggml_backend_graph_compute()` (line 2850, 2870) blocks the **compute worker thread** until the GPU finishes.
- The connection thread is NOT blocked (compute is enqueued, not executed inline).
- `wait_compute_idle()` (line 2939) allows external callers to block until the queue drains — currently only used by `RPC_CMD_EVENT_RECORD` handler (which no longer calls it, per the fix comment at line 3374).

### Tensor Mapping
- `deserialize_tensor()` (line 2421) creates a `ggml_tensor` with `ggml_new_tensor_4d()` but **does not allocate buffer memory**. The tensor's `data` and `buffer` fields are set from the serialized `rpc_tensor` (pointers into server-side GPU memory allocated via `RPC_CMD_ALLOC_BUFFER`).
- `create_node()` (line 2729) reconstructs the computation graph by linking source tensors via a `tensor_map` (id -> ggml_tensor*).

## 4. GRAPH_COMPUTE_ALL Hook Points

### New RPC Command (Command Enum)
- Add `RPC_CMD_GRAPH_COMPUTE_ALL` and `RPC_CMD_GRAPH_RECOMPUTE_ALL` after `RPC_CMD_CHANNEL_BIND` (currently value 20, line 138).
- Update `RPC_CMD_COUNT` accordingly.
- Add request/response structs in the `#pragma pack(push, 1)` block (line 99-658):
  - `rpc_msg_graph_compute_all_req`: `n_devices`, `device_ids[]`, followed by serialized graph.
  - `rpc_msg_graph_compute_all_rsp`: `result` (0 = success).

### Handler Registration
- Add a new `case RPC_CMD_GRAPH_COMPUTE_ALL:` in the switch at line 3101.
- Handler logic:
  1. Read `n_devices` + `device_ids[]` from the input.
  2. Deserialize the remaining bytes as a graph (reuse existing deserialization from `graph_compute()`).
  3. Create a `ggml_backend_sched_t` for the specified devices.
  4. Call `ggml_backend_sched_graph_compute(sched, graph)`.
  5. Send response.

### Server-Side Scheduler Creation (Model After Client-Side Pattern)
`ggml_backend_sched_new()` (ggml-backend.cpp line 2766) takes:
- `ggml_backend_t * backends`: array of backend pointers.
- `ggml_backend_buffer_type_t * bufts`: array of buffer types.
- `int n_backends`: number of backends (including CPU fallback).
- `size_t graph_size`: initial hash table size.
- `bool parallel`: enables pipeline parallelism (multiple copies).
- `bool op_offload`: enables op-level offload.

Server-side pattern (to add to `rpc_server`):
```cpp
ggml_backend_sched_t create_multi_device_sched(
    const uint32_t * devices, uint32_t n_devices,
    const ggml_cgraph * graph) {

    std::vector<ggml_backend_t> dev_backends;
    std::vector<ggml_backend_buffer_type_t> dev_bufts;

    for (uint32_t i = 0; i < n_devices; i++) {
        if (devices[i] >= backends.size()) return nullptr;
        dev_backends.push_back(backends[devices[i]]);
        dev_bufts.push_back(ggml_backend_get_default_buffer_type(backends[devices[i]]));
    }

    // Add CPU backend as fallback (required by ggml_backend_sched_new — last backend must be CPU)
    ggml_backend_t cpu_backend = get_cpu_backend(); // singleton
    dev_backends.push_back(cpu_backend);
    dev_bufts.push_back(ggml_backend_cpu_buffer_type());

    size_t graph_size = graph ? graph->n_nodes : 4096;

    return ggml_backend_sched_new(
        dev_backends.data(), dev_bufts.data(),
        dev_backends.size(), graph_size,
        false,  // no pipeline parallelism server-side (client handles that)
        false   // no op offload
    );
}
```

### Where the Server Splits the Graph

The scheduler handles splitting internally via `ggml_backend_sched_compute_splits()` (called by `ggml_backend_sched_graph_compute_async()`, line 2995). **However, the scheduler CANNOT auto-partition same-type GPUs.**

`ggml_backend_sched_backend_from_buffer()` (line 1160) iterates backends and returns the FIRST one that supports the buffer type and op. For two CUDA backends (3090 + 3070) supporting identical ops and buffer types:

- Backend 0 (3090) matches everything first
- Backend 1 (3070) never gets anything
- **Result: all work goes to 3090, 3070 stays idle**

The scheduler only assigns to 3070 if weight tensors are pre-allocated on it during SET_TENSOR. This means:

**Partition IS weight placement.** The client controls the split by deciding which layer weights go to which GPU. There is no server-side auto-partition for same-type GPUs — the scheduler follows weight buffer locations.

For 3090+3070 (1.75x speed ratio), the high-performance path is:
- Client assigns 64% of layers to 3090, 36% to 3070
- Scheduler naturally places compute on the GPU holding each layer's weights
- Cross-GPU copy inserted at the boundary between fast-GPU and slow-GPU layers
- **Result: balanced compute time (3.04 vs 3.08 ms), +33% throughput**

Equal weight assignment (50/50) would leave the 3070 as bottleneck at 4.2 ms while the 3090 idles at 2.4 ms — a **-25% regression** vs weighted split.

#### Impact on Server-Side Scheduler Design

- No changes needed to `ggml_backend_sched` or its split algorithm
- All partition optimization happens on the CLIENT side (weight placement during SET_TENSOR)
- Server-side scheduler is purely reactive: it runs what the weight placement dictates

After `ggml_backend_sched_reserve(sched, graph)` allocates intermediate buffers, `ggml_backend_sched_graph_compute(sched, graph)` runs the full graph across all devices.

### Returning Results to the Client
- Response format: `rpc_msg_graph_compute_all_rsp { uint32_t result; }`.
- The output tensor remains in server GPU memory (on whichever device the scheduler placed it).
- Client reads it back via existing `RPC_CMD_GET_TENSOR` (no changes needed).
- Optionally include `uint32_t output_device` in the response so the client knows which device holds the output (avoids trial-and-error GET_TENSOR).

## 5. Key Risks

### Thread Safety
- The current `compute_worker_loop()` is single-threaded and serializes all compute. A server-side scheduler would introduce its own internal threading (CUDA streams, async copies).
- **Risk**: `ggml_backend_sched_graph_compute()` calls `ggml_backend_synchronize()` on each backend. If the compute worker thread synchronizes on a backend while another command (e.g., `SET_TENSOR`) is writing to that buffer from the connection thread, we get a data race.
- **Mitigation**: Keep compute on the dedicated worker thread. Non-compute commands (SET_TENSOR, GET_TENSOR, COPY_TENSOR) already touch GPU buffers from the connection thread — these must be synchronized via `wait_compute_idle()` or per-backend locks before the scheduler touches them.

### Memory Management
- `ggml_backend_sched_reserve()` allocates intermediate buffers on each backend via `ggml_gallocr_new_n()`. These are owned by the scheduler and freed in `ggml_backend_sched_free()`.
- **Risk**: The current code stores the deserialized graph in `stored_graphs[device].buffer`. With a scheduler, the graph's tensor allocations come from the scheduler's grapalloc, not from pre-allocated server buffers. The graph object itself (`stored_graphs[device].graph`) points into `stored_graphs[device].buffer` for metadata but tensor data lives in scheduler-allocated buffers.
- **Mitigation**: The scheduler must outlive the graph. Cache the scheduler alongside the graph for recompute (not just the graph). On `graph_recompute()`, re-use the same scheduler instance.

### Backward Compatibility
- Old clients send `RPC_CMD_GRAPH_COMPUTE` per device. New server must handle both.
- New clients send `RPC_CMD_GRAPH_COMPUTE_ALL`. Old server will reject with "Unknown command" (line 3401).
- **Mitigation**: HELLO handshake capability flag. Add `RPC_CAP_MULTI_DEVICE` bit to `rpc_msg_hello_rsp.conn_caps[]`. Client checks this before using `GRAPH_COMPUTE_ALL`; falls back to per-device path otherwise.

### Integration with Event System
- The current pipeline uses `RPC_CMD_EVENT_RECORD` for cross-device ordering. With server-side scheduling, the server handles cross-device copies internally — no client-visible event needed for server-local copies.
- **Risk**: The client's pipeline barrier logic expects an EVENT_RECORD response after each GRAPH_RECOMPUTE. With GRAPH_COMPUTE_ALL, there's one compute, so one EVENT_RECORD is still correct.
- **Mitigation**: The `RPC_CMD_EVENT_RECORD` handler (line 3367) already just echoes back the event_id without waiting for compute. This remains compatible. However, the client's `ggml_backend_rpc_graph_compute()` sends EVENT_RECORD only on the recompute path — for GRAPH_COMPUTE_ALL, the client should send one EVENT_RECORD after receiving the GRAPH_COMPUTE_ALL response.

### Additional Risk: Graph Deserialization
- The current `graph_compute()` deserialization hardcodes `device` from the input. For GRAPH_COMPUTE_ALL, the device field in the serialized graph should be ignored (the device list comes from the header).
- **Mitigation**: Refactor deserialization to take an explicit device parameter (or no device for ALL mode). The `create_node()` logic doesn't use device — it's just pointer patchup — so this is safe.

### Additional Risk: Buffer Lifetime
- Server-side `buffers` set (line 2283) tracks allocated buffers for validation. Scheduler-allocated buffers are NOT in this set. If the client later sends `RPC_CMD_FREE_BUFFER` for a scheduler-allocated buffer, the server will reject it.
- **Mitigation**: The client should NOT free intermediate buffers (they're owned by the scheduler). Only weight buffers (allocated via `RPC_CMD_ALLOC_BUFFER`) should be freed by the client. This is already the case — intermediates are owned by ggml_alloc.
