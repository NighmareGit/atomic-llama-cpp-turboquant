## Prototype Scope

The throwaway implements the full Option B+ protocol as specified in ADR-0004:

### Protocol Layer (Agent A)
- `RPC_CMD_GRAPH_COMPUTE_ALL` (21) and `RPC_CMD_GRAPH_RECOMPUTE_ALL` (22) enum values
- 4 packed structs: `rpc_msg_graph_compute_all_req/rsp`, `rpc_msg_graph_recompute_all_req/rsp`
- `RPC_CAP_MULTI_DEVICE` flag (conn_caps[0] bit 1)
- `server_supports_multi_device` field on `socket_t`
- Server advertises capability during HELLO handshake (both v3 and v4 paths)
- Client reads capability from conn_caps after HELLO

### Server Handler (Agent B)
- `create_multi_device_sched()` — creates a `ggml_backend_sched` spanning multiple
  server GPUs with CPU fallback
- `graph_compute_all()` — deserializes the ALL-format graph (n_devices + device_ids +
  graph_data sans leading device field), creates multi-device scheduler, computes,
  stores graph for recompute
- `graph_recompute_all()` — retrieves stored graph by first device index, recreates
  scheduler, recomputes
- `enqueue_graph_compute_all()` / `enqueue_graph_recompute_all()` — async compute
  worker dispatch
- Switch cases for both commands in `rpc_serve_client()`

### Client Dispatch (Agent C)
- `n_devices_on_endpoint` and `is_multi_device_capable` on `ggml_backend_rpc_context`
- `serialize_graph_for_all()` — serializes graph without the leading device field
- Multi-device path in `ggml_backend_rpc_graph_compute()` — early-return branch before
  existing single-device logic
- `rpc_get_n_devices_on_endpoint()` — queries server via `RPC_CMD_DEVICE_COUNT`
- Endpoint capability detection at backend init time
- `RPC_WEIGHT_SPEED_RATIO = 1.75f` constant + weighted placement documentation

## Key Findings

### 1. Protocol Design is Sound

The packed struct alignment (all sizes are multiples of 4 bytes), wire format
(n_devices + device_ids + standard graph serialization), and capability
advertisement all work without modification. No layout issues found.

**Struct sizes:**
| Struct | Size | Notes |
|--------|------|-------|
| `rpc_msg_graph_compute_all_req` | 44 bytes | 4 fields + 8-device array (32B) |
| `rpc_msg_graph_compute_all_rsp` | 8 bytes | result + output_device |
| `rpc_msg_graph_recompute_all_req` | 52 bytes | 4 fields + 8-device array + graph_hash |
| `rpc_msg_graph_recompute_all_rsp` | 8 bytes | result + output_device |

### 2. Capability Advertising Works with Existing Pattern

Using `rsp.conn_caps[0] |= RPC_CAP_MULTI_DEVICE` in `rpc_serve_client()` (after
`sock->get_caps()`) correctly advertises the capability on both v3 and v4 HELLO
paths. The client reads it via `response.conn_caps[0] & RPC_CAP_MULTI_DEVICE`.

**Important:** Capability-bit approach is preferred over minor version gating.
Agent C initially used `minor >= 5`, which is fragile (requires a version bump).
The merged version uses the bit flag, matching how `RPC_CAP_TRACE_ID` works.

### 3. Key Risk: `init_sock` Lifetime in `ggml_backend_rpc_init()`

**Risk level: MEDIUM**

In `ggml_backend_rpc_init()`, the prototype queries `get_socket(endpoint)` during
backend initialization to determine `n_devices_on_endpoint` and
`is_multi_device_capable`. However, `get_socket()` returns a shared socket that
may not yet have completed HELLO negotiation at the time `rpc_init` is called.

**Root cause:** The socket is created on first access via `get_socket()`. The
HELLO handshake (`negotiate_hello()`) happens separately, typically when the
socket is first used for a command. If `rpc_init` is called before the socket
has completed HELLO, `server_supports_multi_device` will be `false`.

**D4.5 fix:** Move the capability check to a deferred init point, or store the
capability bit from the HELLO response in the endpoint-level registry (not the
per-backend context). Options:
- (a) Store it in `rpc_trace_emit_hello` / endpoint metadata registry
- (b) Lazy-init the fields on first `graph_compute` call
- (c) Ensure `rpc_init` is called after socket connection + HELLO in all paths

### 4. Key Risk: `ggml_backend_sched` Leaks on `graph_compute_all()`

**Risk level: LOW**

The server destroys the multi-device scheduler after each `graph_compute_all()`
call via `ggml_backend_sched_free()`. This is correct for the prototype but
adds allocation overhead on every token. For `graph_recompute_all()`, the
scheduler is also destroyed and recreated.

**D4.5 fix:** Cache the multi-device scheduler (keyed by device list) and reuse
it across compute calls. The scheduler's internal state can be reset between
calls rather than destroyed and recreated.

### 5. Implementation Correction: CPU Backend API

`ggml_backend_init_cpu()` does not exist in the codebase. The prototype uses
`ggml_backend_init_by_type(GGML_BACKEND_DEVICE_TYPE_CPU, nullptr)` instead,
which is declared in `ggml-backend.h` (already included).

**D4.5 consideration:** The CPU fallback backend may not be needed if all
computations can be placed on server GPUs. Evaluate whether the fallback is
necessary or can be removed.

### 6. Implementation Correction: Server-Side `stored_graphs` Has One Slot Per Device

The prototype stores the ALL-mode graph at index `devices[0]` in the existing
`stored_graphs` vector. This works because the first device index is always the
store key. However, if the same device is used in multiple ALL-mode configurations,
the stored graph gets overwritten.

**D4.5 fix:** Add a dedicated `stored_graph_all` field to `rpc_server` or use
a map keyed by (device_set_hash) to avoid conflicts with single-device stored
graphs.

### 7. Serialization Redundancy

The `serialize_graph_for_all()` function is nearly identical to the existing
`serialize_graph()` except it omits the leading `device` field and adds
`n_devices + device_ids`. This duplication is acceptable for the throwaway
prototype.

**D4.5 consideration:** Refactor to a single serialization function that
optionally includes the device prefix, or keep the ALL format as the canonical
format and adapt the existing `GRAPH_COMPUTE` path to wrap it.

## Multi-Agentic Development Assessment

Three worktree-isolated sub-agents were dispatched in parallel:

- **Agent A** (protocol layer): 26 tool calls, 229s - clean, no issues
- **Agent B** (server handler): 70 tool calls, 609s - clean, adapted CPU backend API
- **Agent C** (client dispatch): 85 tool calls, 890s - 2 issues (capability gating, syntax error)

**Merge conflicts resolved:**
1. Struct layouts: Agent C used simplified structs without `sync_mode`/`output_requested`.
   D4.4 spec structs (Agent A/B) were kept.
2. Capability gating: Agent C used `minor >= 5`, merged to cap-bit approach (Agent A).
3. Syntax error: Agent C had a missing template argument on line 2208
   (`duration_cast<std::chrono::microseconds>(` missing), fixed during merge.

**Assessment:** Worktree isolation works well for this type of task. The shared
contract specification is critical — all agents must agree on exact enum values,
struct layouts, and constant names. Without this, conflicts are guaranteed.
