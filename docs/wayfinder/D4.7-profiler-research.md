# D4.7 — Profiler Research: Binary Design + Heatmap Schema

**Ticket:** D4.7
**Type:** research (read/write — design artifact only, no code changes)
**Date:** 2026-07-11
**Status:** complete
**Outputs:** this document; feeds D4.8 prototype, D4.9 ADR

## 1. Executive Summary

The profiler binary (`llama-gpipe-profiler`) extends an existing, proven
stack: `llama-bench` (in `tools/llama-bench/`) provides the structural
template; `llama-pipeline-profiler` (in `tools/llama-pipeline-profiler/`)
provides the multi-GPU RPC orchestration, trace capture, diagnose, and
regression machinery. Three trace formats already exist (`sched-trace.jsonl`,
`rpc-trace.jsonl`, `pipeline-trace.jsonl`) and are consumed by Python gate
scripts. The new binary adds (a) task-stratified profiling (pp vs tg),
(b) a heatmap JSON schema, and (c) KV cache timing capture.

Key decision: **KV cache profiling should be collected via server-side
telemetry appended to `GRAPH_COMPUTE_ALL` responses**, not by instrumenting
`llama_kv_cache` directly on the client. Rationale in section 5.

### 2.3 Trace Formats

#### `sched-trace.jsonl` (`GGML_SCHED_TRACE=1`)

Per graph-split event from `ggml-backend.cpp`. Base fields:

```json
{"ts_us":123,"trace_id":1,"split":1,"backend":2,"copy":0,"phase":"split_total","elapsed_us":9623}
```

When `GGML_PIPELINE_TRACE` is also on, `decode_id` is prepended. When
`sched_trace_emit_sync_detail` fires (input wait >50us), extended fields
appear: `tensor`, `nbytes`, `view`, `src_buft`, `dst_buft`,
`input_backend`, `split_backend`, `host_src`, `host_dst`, `rpc_src`,
`rpc_dst`, `reject`.

Observed phases: `split_total`, `input_wait_copy`, `graph_compute_async`,
`event_record`, `event_wait_slot`, `producer_event_wait`,
`rpc_download_issue`, `host_h2d_issue`, `rpc_relay_flush`,
`event_wait_producer_slot`, `rpc_gather_prefetch_early`,
`rpc_prefetch_start`, `rpc_gather_flush`, `sync_copy_fallback`,
`copy_async_ok`, `rpc_early_flush`, `wf_gather_flush_skip`.

#### `rpc-trace.jsonl` (`GGML_RPC_TRACE=1`)

Per RPC op from `ggml-rpc.cpp`:

```json
{"ts_us":123,"fn":"send_rpc_cmd","phase":"send_recv","cmd":8,"bytes":16,"blocking":true,"elapsed_us":412}
```

Hotpath fields appended when pipeline trace context is active:
`decode_id`, `trace_id`, `split`, `backend`. Special emits:
`negotiate_hello` (endpoint, minor, peer_copy), `copy_issue` (src/dst
endpoint, peer_copy, defer). Server-side emits `server_compute` for
`graph_compute` / `graph_recompute` / `graph_compute_all` /
`graph_recompute_all`.

#### `pipeline-trace.jsonl` (`GGML_PIPELINE_TRACE=1`)

High-level pipeline barrier events:

```json
{"ts_us":123,"event":"pipeline_barrier","decode_id":42,"trace_id":1,"copy_from":0,"copy_to":1,"n_copies":4,"elapsed_us":85}
```

Events: `pipeline_barrier`, `pipeline_barrier_sync`,
`wavefront_depth_release`.

**Consumption:** `pipeline-trace-parse.cpp` produces `trace-summary.txt`
(text summary with per-RPC-op counts, blocking ms, drain_flush, per-backend
split counts/times, overlap stats). `pipeline-diagnose.cpp` produces
`diagnose.json`. Python gate scripts (`b6-gate-phase0-assembly-bounds.py`)
consume `sched-trace.jsonl` directly.

### 2.5 Gate Scripts

`scripts/b6-gate-phase0-assembly-bounds.py` reads `sched-trace.jsonl` and
produces a Phase 0 assembly-bound report: per-decode vs global timeline
concurrency, intra/cross token overlap ceilings, split granularity, and a
work-package classification (W1/W2/depth). It also reads `diagnose.json`
for `overlap_pct`, `G_tps`, `straggler_backend`. Output is both human
readable and `--json` machine-readable.

## 3. Heatmap Schema Design

The heatmap is the profiler's primary output — a task-stratified,
per-layer, per-GPU timing snapshot consumed by the Pareto optimizer
(D4.11+). Schema is forward-compatible: unknown keys are ignored by
consumers, new keys are additive.

### 3.1 Top-Level Structure

```json
{
  "schema_version": 1,
  "generated_at": "2026-07-11T12:00:00Z",
  "git_sha": "abc1234",
  "label": "qwen36-35b-triton-2gpu",
  "model": {
    "path": "/models/Qwen3.6-35B-A3B.gguf",
    "n_layers": 60,
    "n_experts": 128,
    "param_count_b": 36.0,
    "ctx_size": 4096
  },
  "tasks": { ... },
  "gpu_metadata": [ ... ],
  "summary": { ... }
}
```

### 3.2 Task Stratification

```json
"tasks": {
  "pp": {
    "n_prompt_tokens": 512,
    "n_batch": 512,
    "wall_ms": 1250.3,
    "tps": 409.6,
    "layers": [ { "idx": 0, "ms": 18.2, "gpu_id": 0 }, ... ],
    "kv": { "read_ms": 1.1, "write_ms": 0.8, "evict_count": 0 }
  },
  "tg": {
    "n_gen_tokens": 128,
    "wall_ms": 3850.0,
    "tps": 33.2,
    "layers": [ { "idx": 0, "ms": 58.1, "gpu_id": 0 }, ... ],
    "kv": { "read_ms": 0.05, "write_ms": 0.03, "evict_count": 2 }
  }
}
```

### 3.3 Per-Layer Entry

| Field | Type | Description |
|-------|------|-------------|
| `idx` | int | Layer index (0-based) |
| `ms` | float | Compute time (ms) for this layer |
| `gpu_id` | int | GPU that executed this layer |
| `is_moe` | bool | Whether this is a MoE FFN layer |
| `experts_active` | int[] | Which experts fired (MoE only; tg typically 2-3) |
| `tensor_activations` | string[] | Names of tensors computed (optional, for deep analysis) |

### 3.4 GPU Metadata

```json
"gpu_metadata": [
  {
    "id": 0,
    "name": "NVIDIA RTX 3090",
    "backend": "CUDA",
    "vram_total_mib": 24576,
    "vram_used_mib": 18200,
    "pci_bus_id": "0000:01:00.0",
    "pci_link_gen": 4,
    "pci_link_width": 16,
    "sm_count": 82,
    "clock_mhz": 1695
  }
]
```

### 3.5 KV Cache Timing

```json
"kv": {
  "read_ms": 1.1,
  "write_ms": 0.8,
  "evict_count": 0,
  "slots_active": 1,
  "slots_total": 8,
  "slot_timings_us": [ { "slot": 0, "read": 45, "write": 30 }, ... ]
}
```

### 3.6 Summary Section

```json
"summary": {
  "straggler_gpu": 1,
  "straggler_ms_per_tok": 58.1,
  "overlap_pct": 0.2,
  "gate_s5": "PASS",
  "gate_b6": "FAIL",
  "gpu_smell_flags": [],
  "total_power_w": 320.5
}
```

### 3.7 Forward-Compatible Pareto Hook

The `layers[]` array and `gpu_metadata[]` together let the optimizer
estimate: for any candidate layer-to-GPU reassignment, the new per-GPU
compute time is the sum of assigned layer `ms` values. The optimizer can
model `pp` and `tg` separately (MoE expert routing differs). The
`experts_active` field enables expert-placement optimization (put hot
experts on fast GPU). Schema extensibility: a future `memory_pressure`
object can be added without breaking existing consumers.

## 4. Binary CLI Design

Patterned after `llama-bench` + `llama-pipeline-profiler`. The binary name
is `llama-gpipe-profiler`, living in `tools/llama-gpipe-profiler/`.

### 4.1 Core Flags

| Flag | Default | Purpose |
|------|---------|---------|
| `-m, --model` | (required) | GGUF path |
| `-rpc, --rpc` | (local only) | Comma-separated RPC endpoints |
| `-ts, --tensor-split` | equal | Per-device weights |
| `--tasks` | `pp,tg` | Comma-separated task list: `pp`, `tg`, `spec` (speculative) |
| `-p, --n-prompt` | 512 | Prompt tokens (pp task) |
| `-f, --file` | (none) | Prefill from prompt text file |
| `-n, --n-gen` | 128 | Generation tokens (tg task) |
| `-r, --repeat` | 5 | Repetitions per task |
| `--warmup` | 1 | Warmup tokens (default on; `--no-warmup` to disable) |
| `-o, --output` | `heatmap.json` | Output path |
| `--format` | `json` | Output format: `json`, `jsonl` |
| `--out-dir` | `./profiler-out` | Artifact root |
| `--trace` | off | Enable sched/rpc/pipeline traces |
| `--with-gpu-telemetry` | off | nvidia-smi CSV sampler |
| `-ngl, --n-gpu-layers` | 99 | GPU layers |
| `-sm, --split-mode` | layer | Split strategy |
| `-ctk, --cache-type-k` | q4_0 | KV cache K type |
| `-ctv, --cache-type-v` | q4_0 | KV cache V type |
| `-b, --batch-size` | 512 | `n_batch` |
| `-ub, --ubatch-size` | 512 | `n_ubatch` |
| `-t, --threads` | auto | Thread count |
| `--ctx-size` | 4096 | Context size |
| `--server-telemetry` | off | Request `GGML_RPC_SERVER_TELEMETRY` from endpoints |
| `--overlap-target` | 5 | B+6 gate threshold |
| `-h, --help` | — | Usage |

### 4.2 Design Rationale

- **`--tasks pp,tg`**: drives the task-stratified design. Each task runs
  as a separate `run_session`-like cell. `pp` runs prompt processing
  (batched `llama_decode` of `-p` tokens); `tg` runs token generation
  (serial `llama_decode` of `-n` tokens). `spec` (deferred to v2) would
  drive speculative decoding patterns.
- **`--server-telemetry`**: opt-in flag that sets
  `GGML_RPC_SERVER_TELEMETRY=1` so the server appends per-device timing
  to both `GRAPH_COMPUTE` (single-device) and `GRAPH_COMPUTE_ALL`
  (multi-device) responses. Without this flag, only client-side
  traces are available.
- **Output**: single `heatmap.json` by default (the synthesized product).
  Raw traces land under `--out-dir/telemetry/` when `--trace` is on.
- **Repetitions**: trace capture on last rep only (matches existing
  `llama-pipeline-profiler` behavior — trace on final rep avoids
  first-rep cache effects while keeping overhead off the timed reps).

### 4.3 CMake Target

```
llama-gpipe-profiler-impl  (library)  <- all logic
llama-gpipe-profiler       (exe)      <- main.cpp
  links: llama-gpipe-profiler-impl, llama-common, llama, [ggml-rpc]
```

Location: `tools/llama-gpipe-profiler/`. Mirrors `llama-bench` exactly.

## 5. KV Cache Profiling Decision

### Option A — Instrument `llama_kv_cache` Directly (Client-Side)

Add timing hooks in `src/llama-kv-cache.cpp` (`find_slot`, stream copy
paths). Emit per-slot read/write timing via a new `GGML_KV_TRACE` env
var -> `kv-trace.jsonl`.

| Pros | Cons |
|------|------|
| No server changes | Client-side only — misses server-local KV ops on Path C |
| Simple jsonl format | Adds hot-path overhead on every decode |
| | KV cache impl is stream/multi-type complex (iswa, dsa variants) |
| | Cannot capture server-side KV placement for `GRAPH_COMPUTE_ALL` |

### Option B — Server Telemetry via `GRAPH_COMPUTE_ALL` Response (Recommended)

Extend the `rpc_msg_server_telemetry` frame (defined in D4.8 prototype)
with `kv_read_times_us[]` and `kv_write_times_us[]`. Server instruments
KV ops internally, appends timing to the compute response.

| Pros | Cons |
|------|------|
| Captures server-local KV ops (Path C) | Requires server-side code changes |
| No client hot-path overhead | Only available when server supports it |
| Aligns with Pareto optimizer data needs | Needs capability negotiation (HELLO) |
| Per-slot breakdown natural on server | |

### Decision

**Option B** (server telemetry). Rationale:
1. The profiler targets Path C (server-side multi-GPU scheduling) where
   KV cache ops happen server-side. Client-side instrumentation is
   blind to this.
2. Hot-path overhead on the client would corrupt the very timing being
   measured.
3. The Pareto optimizer (D4.11+) needs server-side KV placement data
   that only the server can provide.
4. Graceful degradation: if the server does not advertise
   `RPC_CAP_SERVER_TELEMETRY`, the profiler falls back to client-side
   estimates (total KV time from `input_wait_copy` phase) and marks the
   heatmap `kv_source: "estimated"`.

## 6. Task-Awareness Approach

### 6.1 Driving Prompt Processing vs Token Generation

The llama.cpp inference API naturally stratifies:

- **PP (prompt processing)**: batched `llama_decode(ctx,
  llama_batch_get_one(tokens, n_tokens))` where `n_tokens` = batch size.
  All tokens processed in parallel. KV cache writes dominate.
- **TG (token generation)**: serial `llama_decode(ctx,
  llama_batch_get_one(&token, 1))` per token. KV cache reads dominate.
  Compute-bound.

The profiler runs these as separate cells (like llama-bench's `n_prompt`
and `n_gen` vectors), producing independent heatmap `pp` and `tg` sections.

### 6.2 Capturing Per-Task Tensor/Layer Activation Patterns

| Mechanism | What it captures | Task relevance |
|-----------|------------------|----------------|
| `sched-trace.jsonl` (per-split timing) | Per-backend, per-split compute time | Both pp/tg |
| Server telemetry `device_timings_us[]` | Per-GPU compute time | Both |
| Server telemetry `layer_assignments[]` | Layer-to-GPU mapping | Both |
| `experts_active` per layer | Which MoE experts fired | **TG-specific** (routing varies per token) |
| KV slot timings | Per-slot read/write | **PP-dominated** (bulk write) vs **TG** (streaming read) |

The critical insight: **MoE expert routing differs between pp and tg**.
During pp, the full prompt sees aggregate expert activation. During tg,
each token routes to a specific 2-3 expert subset. The heatmap captures
`experts_active` per layer per task so the optimizer can model expert
placement separately for each phase.

### 6.3 Implementation Strategy

1. Run `--tasks pp,tg` as separate cells with independent trace capture.
2. For TG: enable server telemetry to get per-token layer timing and
   expert activation. Aggregate across `--repeat` runs.
3. For PP: capture batched layer timing. KV write timing is the key
   metric here.
4. Synthesize: the profiler post-processes raw telemetry into the
   heatmap `layers[]` array using per-layer aggregation (p50, p95, mean).

## 7. Recommendations for D4.8

1. **Start with the telemetry wire format.** D4.8 should prototype the
   `rpc_msg_server_telemetry` frame with all 6 fields (device_timings_us,
   layer_assignments, copy_times_us, device_meta, kv_read_times_us,
   kv_write_times_us). Validate overhead is <1% on the hot path.

2. **Validate KV collection cost.** Measure the cost of instrumenting
   `find_slot` + stream copy paths server-side. If >50us per decode,
   sample (every Nth token) rather than capture-all.

3. **Capability negotiation.** Add `RPC_CAP_SERVER_TELEMETRY` to the
   HELLO handshake so the client can degrade gracefully when the server
   does not support it.

4. **Thin client first.** Before building the full profiler binary,
   validate end-to-end: connect to RPC endpoint, exercise
   `GRAPH_COMPUTE_ALL`, parse telemetry, write raw JSON. This de-risks
   the wire format before investing in CLI/heatmap synthesis.

5. **Reuse `llama-pipeline-profiler` infrastructure.** The new binary
   should borrow its RPC registration (`register_rpc_servers`), trace env
   setup (`setup_trace_env`), and mode dispatch patterns. Do not
   reimplement — refactor shared code into `llama-pipeline-profiler-impl`
   or a new `llama-profiler-common` library.

6. **Schema versioning.** Start at `schema_version: 1` with additive-only
   evolution. The Pareto optimizer will be a consumer; coordinate field
   naming with D4.11 design.

7. **Spike: MoE expert activation capture.** Determine whether the
   server can cheaply report which experts fired per layer per token.
   This is the highest-value, highest-uncertainty field for the
   optimizer. If unavailable, the heatmap omits `experts_active` and
   the optimizer falls back to uniform-expert assumptions.
