# D5.1 — Split Timing Analysis: Sub-Stage Boundaries for Deeper Pipelining

**Date:** 2026-07-11
**Source traces:** `/tmp/d41-baseline/` (D4.1 romulus dual-GPU baseline)
**Hot paths reference:** `docs/hot-paths-analysis.md`
**Inputs:** D4.1 trace data, D4.6 GRAPH_COMPUTE_ALL telemetry, D2.2 performance results

---

## 1. Current Pipeline Structure

The existing Path D 2-stage GPipe (Mode A) has:

```
Stage 0 (compute): embed + RPC compute splits + local compute splits
Stage 1 (gather):  gather + KV write + sample
```

The scheduler dispatches all splits in `Stage 0` serially before recording
a `compute_done` event. Stage 1 waits on that event, then runs the gather
split. This means the entire compute chain must complete before any gather
can begin -- the full sequential bottleneck.

### 2.2 Key Observations

1. **Cold vs warm variance is extreme.** The first decode spends 59.8 ms in Stage 0;
   subsequent decodes drop to 15.7 ms -- a 3.8x speedup from CUDA graph caching and
   hash deferral warmup.

2. **rpc_prefetch_drain dominates cold-path RPC.** 15.2 ms of the initial RPC split
   is spent draining deferred hash uploads. This is a one-time cost.

3. **Split 1 (RPC 3060 Ti) dominates warm-path compute.** At 10.0 ms (63.8%), it is
   1.8x the time of Split 2 (ROCm 7900 XTX, 5.7 ms). This is the opposite of what
   raw TFLOPS would predict -- the 7900 XTX is mathematically faster but the RPC
   overhead (PCIe 1.0 x4 chipset-attached, RTT) makes Split 1 the straggler.

4. **Split 0 (embed) is trivially cheap.** 11-64 us, less than 1% of Stage 0 time.
   It is a natural first sub-stage that can dispatch immediately.

## 3. Deeper Pipeline Sub-Stage Boundaries

The analysis supports splitting Stage 0 into **3 per-backend sub-stages** for the
romulus dual-GPU test bench, and up to **5 sub-stages** for the production 5-GPU
topology:

### 3.1 Romulus Dual-GPU (2-GPU RPC)

```
Sub-stage 0: embed        (CPU,     11 us,  <0.1%  of Stage 0)
Sub-stage 1: RPC0 compute (3060 Ti, 10,017 us, 63.8% of Stage 0)
Sub-stage 2: ROCm compute (7900 XTX, 5,682 us, 36.2% of Stage 0)  [includes output]
```

**Pipeline diagram:**

```
Token T:   [emb(T)] [RPC0(T) ...............] [ROCm(T) ........]
Token T+1:         [emb(T+1)][RPC0(T+1)................][ROCm(T+1)........]
```

**Overlap benefit:** ROCm(T) and RPC0(T+1) run concurrently. Since ROCm is ~5.7 ms
and RPC0 is ~10 ms, the overlap saves max(0, min(5.7, 10.0)) = 5.7 ms per token.
Effective throughput: 15.7 ms -> 10.0 ms per token = +57% improvement.

### 3.2 Production 5-GPU (romulus cluster)

Per D0.2 split topology and D4.1 findings:

```
Sub-stage 0: embed        (CPU,            <0.1%)
Sub-stage 1: RPC0 compute (remus 5060,     2.1 ms est.)
Sub-stage 2: RPC1 compute (romulus 3060,   4.0 ms est.)  [straggler]
Sub-stage 3: RPC2 compute (triton 3090,    3.2 ms est.)
Sub-stage 4: RPC3 compute (triton 3070,    3.5 ms est.)
```

**Pipeline diagram for 5 sub-stages:**

```
Token T:   [emb][RPC0][RPC1 .....][RPC2 ...][RPC3 ..]
Token T+1:      [emb][RPC0][RPC1 .....][RPC2 ...][RPC3 ..]
```

**Straggler analysis:** RPC1 (romulus 3060) at ~4.0 ms is the bottleneck.
The pipeline cycle time is bounded by max(sub-stage). With 5 sub-stages,
`cycle_time = max(embed, RPC0, RPC1, RPC2, RPC3) = 4.0 ms`.

Compare to serial dispatch: 0.01 + 2.1 + 4.0 + 3.2 + 3.5 = 12.8 ms.
Theoretical speedup: 12.8 / 4.0 = 3.2x.

## 4. Straggler Impact Assessment

### 4.1 Identifying the Straggler

From the D4.1 trace data and D0.2 topology analysis:

| GPU | Role | Per-token Time | Straggler? |
|-----|------|:-------------:|:----------:|
| CPU | embed | 11 us | No |
| 3060 Ti (romulus) | RPC0, early layers | 10,017 us | **Yes (2-GPU test bench)** |
| 7900 XTX (romulus) | ROCm, late layers | 5,682 us | No |
| 5060 (remus) | RPC0, production | 2.1 ms est. | No |
| 3060 (romulus) | RPC1, production | 4.0 ms est. | **Yes (production)** |
| 3090 (triton) | RPC2, production | 3.2 ms est. | No |
| 3070 (triton) | RPC3, production | 3.5 ms est. | No |

### 4.2 Straggler Amplification in GPipe

In a 2-stage pipeline, the straggler blocks ALL subsequent backends. Even if
ROCm0 finishes in 5.7 ms, it must wait for RPC0 to finish its 10 ms + cross-GPU
transfer before it can proceed.

With per-backend sub-stages, RPC0's 10 ms no longer blocks ROCm0 -- they are
independent pipeline stages. ROCm0 can begin its work on token T while RPC0 is
still computing token T (both processing different tokens in the pipeline).

### 4.3 Mitigation Strategies

| Strategy | Mechanism | Expected Gain |
|----------|-----------|:------------:|
| Sub-stage isolation | Split Stage 0 into per-backend sub-stages | +57% (2-GPU), +3.2x (5-GPU) |
| Load balancing | Give straggler fewer layers (already done: ts=45/55) | Already applied |
| Adaptive depth | Skip sub-stages for homogeneous backends with similar timing | TBD from D5.6 |
| GRAPH_COMPUTE_ALL | Batch RPC compute server-side (D4.5, already done) | Already applied |

## 5. Sub-Stage Boundary Mapping

### 5.1 Semantics

| Sub-stage Number | Name | What it Does | Produces | Consumes |
|:---:|------|-------------|----------|----------|
| 0 | `embed` | Token embedding lookup + positional encoding | `inp_embd` tensor on device | Token IDs from sample output |
| 1 | `rpc_backend_0` | Forward pass through layers assigned to first RPC backend | Intermediate activations | `inp_embd` from sub-stage 0 |
| 2 | `rpc_backend_1` | Forward pass through layers assigned to second RPC backend | More intermediate activations | Output from sub-stage 1 |
| 3 | `rpc_backend_2` | Forward pass through layers assigned to third RPC backend | ... | Output from sub-stage 2 |
| 4 | `rpc_backend_3` | Forward pass through layers on fourth RPC backend | Output hidden states | Output from sub-stage 3 |

Note: On the romulus dual-GPU test bench (2 backends), only sub-stages 0-2
are active. Sub-stages 3-4 are for production 5-GPU topology.

### 5.2 Event Signaling Protocol

Each sub-stage boundary uses per-backend events:

```
Sub-stage 0 (embed):
    compute embed -> record(event[0])

Sub-stage 1 (RPC0):
    wait(event[0]) -> compute RPC layers -> record(event[1])

Sub-stage 2 (ROCm):
    wait(event[1]) -> compute local layers + output -> record(event[2])

Stage 1 (gather):
    wait(event[2]) -> gather + KV write -> record(kv_ready for next token)
```

Cross-token overlap:

```
Token T sub-stage 1 records event[1]
Token T+1 sub-stage 0 records event[0]
Token T+1 sub-stage 1 waits on both event[0] (embed ready) and event[1] (RPC0 done with T)
```

## 6. Pipeline Depth vs Benefit Analysis

| n_stages | Decomposition | Cycle Time (ms) | Speedup vs 2-stage |
|:-------:|--------------|:---------------:|:------------------:|
| 2 (current) | [emb+RPC+ROCm] + [gather] | 15.7 | 1.0x (baseline) |
| 3 | [emb] + [RPC] + [ROCm+gather] | 10.0 | 1.57x |
| 4 | [emb] + [RPC] + [ROCm] + [gather] | 10.0 | 1.57x |
| 5 (full) | [emb] + [RPC0] + [RPC1] + [RPC2] + [ROCm+gather] | 4.0 | 2.5x (est.) |

**Key finding:** The 3-stage pipeline captures most of the benefit (+57%).
Splitting ROCm from gather (4-stage) adds negligible gain because gather
is cheap (<0.1 ms). The 5-stage pipeline requires the production cluster
but promises a 3.2x cycle-time reduction by isolating the straggler.

## 7. Adaptive Depth Recommendation

Based on the timing analysis:

### 7.1 When to Use n_stages=2 (current)

- Single GPU (no RPC)
- Homogeneous backends with similar per-layer timing
- Test/CI environments where simplicity matters

### 7.2 When to Use n_stages=3

- Dual-GPU with one RPC backend (current romulus setup)
- Captures 1.57x benefit with minimal additional complexity
- Good default for heterogeneous 2-GPU

### 7.3 When to Use n_stages=4+

- 3+ backends with measurable timing variance
- Straggler isolation needed (one backend 2x+ slower than others)
- Production cluster deployments

### 7.4 Adaptive Strategy

The pipeline depth should be runtime-configurable via `GGML_SCHED_GPIPE_DEPTH`
(n_stages) and adapt to the actual backend topology:

```
n_stages = min(
    GGML_SCHED_GPIPE_DEPTH,     // user override
    n_backends + 1,             // embed sub-stage + per-backend + gather
    LLAMA_GPIPE_MAX_STAGES       // hard limit (8)
)
```

When `GGML_SCHED_GPIPE_DEPTH` is unset or 0, default to:
- 3 stages if exactly 2 backends (dual-GPU RPC)
- 2 stages otherwise (safe default, matches current behavior)

---

## 8. Findings Summary

1. **Split 0 (embed) is a natural first sub-stage** -- 11 us, trivially cheap.

2. **Split 1 (RPC 3060 Ti) is the straggler on romulus dual-GPU** -- 10 ms
   dominates the 5.7 ms Split 2. Isolating it as a sub-stage prevents it
   from blocking the 7900 XTX.

3. **RPC1 (3060) is the expected straggler on production cluster** -- 4.0 ms,
   well above the 2.1-3.5 ms range of other backends.

4. **3 sub-stages are sufficient for dual-GPU.** Embed + RPC + ROCm captures
   the full overlap benefit (+57% cycle time reduction). Adding a separate
   gather sub-stage yields no additional gain.

5. **5 sub-stages needed for production 5-GPU.** Each RPC backend becomes
   its own pipeline stage, enabling RPC2 to compute T+2 while RPC1 finishes T.
   Expects 3.2x cycle-time reduction.

6. **Adaptive depth should default to n_backends+1** -- embed sub-stage plus
   one per backend. User can override via `GGML_SCHED_GPIPE_DEPTH` for tuning.
