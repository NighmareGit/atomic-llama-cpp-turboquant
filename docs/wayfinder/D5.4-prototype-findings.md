# D5.4 — Prototype Findings: Per-Backend Sub-Stage Dispatch

**Date:** 2026-07-11
**Type:** Throwaway prototype — keep findings, delete code
**Test:** `tests/test-gpipe-deeper-prototype.cpp` (deleted after validation)
**Inputs:** D5.1 split timing analysis, D5.3 spec, ADR-0003

---

## 1. Prototype Goals

Validate the feasibility of extending the 2-stage GPipe event system to `n_stages > 2`
with per-backend sub-stages:

1. Can `ggml_sched_gpipe_init()` allocate events for 3-8 stages without crash?
2. Does `record/wait` work in sequential order for n_stages=5?
3. Does cross-token event reuse (T and T+1 sharing the same event slots) work or deadlock?
4. Can a simulated straggler stage be isolated without breaking the pipeline?

## 3. Key Findings

### Finding 1: Event system already supports n_stages > 2 ✅

The existing `ggml_sched_gpipe_init/record/wait` functions at
`ggml/src/ggml-backend.cpp:2838-2895` already handle arbitrary stage counts
up to `GGML_SCHED_MAX_STAGES=8`. No changes needed to the event API.

**Evidence:** `ggml_sched_gpipe_init(sched, 5)` allocates 5 events on the
gather backend. `record(stage_id)` and `wait(stage_id)` work for all stages.
`wait(-1)` drains all stages.

### Finding 2: Sequential record/wait is deadlock-free ✅

The pattern used by the state machine -- record stage 0, wait 0 + record 1,
wait 1 + record 2 -- does not deadlock on CPU backends. The `event_wait`
(and `event_synchronize` fallback) correctly block until the previous
stage's record is complete.

**Evidence:** 3 tokens through a 5-stage pipeline completed without deadlock
or assertion failure.

### Finding 3: Cross-token event reuse requires care ⚠️

The current design uses a **single event per stage** (`gpipe_events[0..n-1]`).
When two tokens (T and T+1) share the same stage events, the protocol is:

```
Token T:   record[0] → record[1] → record[2]
Token T+1:               record[0] → record[1] → record[2]
```

If Token T+1 records `event[0]` before Token T finishes `event[2]`, then
Token T+1's `wait(event[1])` may see Token T's stale `event[1]` instead of
Token T+1's expected `event[1]`. This is **ambiguous signaling** -- the
event timestamp is overwritten by the second record.

**Mitigation:** In GPipe mode A (single-sequence), tokens arrive sequentially:
each token must complete all stages before the next token begins any stages.
Therefore, cross-token event reuse is NOT a problem -- Token T always
finishes all stages before Token T+1 starts.

For future Mode B (multi-seq microbatch), this becomes a real problem.
Mode B will need double-buffered events (even/odd tokens use different
event slots) or per-token event arrays. This is documented as a
**D6 risk** for the multi-seq implementation.

### Finding 4: Straggler isolation requires per-backend stage assignment ✅

The prototype simulates a straggler (10ms sleep in stage 1) but because
it runs on a single-threaded CPU backend, there is no actual parallelism
-- all stages are serial.

On real GPU hardware with concurrent CUDA/HIP streams, per-backend
sub-stages enable the intended overlap: fast backend (ROCm0, stage 2)
can process token T while the straggler (RPC0, stage 1) is still
processing token T+1.

**Key insight:** The throughput benefit comes from **GPU-level concurrency**
(separate CUDA streams on different devices), not CPU-level threading.
The CPU state machine is just a dispatcher; the real overlap happens on
the GPU backends.

### Finding 5: Existing GPipe decode state machine needs minimal changes ✅

The current `llama_decode_gpipe_impl()` (2-stage switch) can be extended
to a loop-based approach without changing its structure:

```cpp
for (int stage = 0; stage < n_stages; stage++) {
    if (stage > 0) ggml_sched_gpipe_wait(sched, stage - 1);
    compute_backend_split(stage);
    ggml_sched_gpipe_record(sched, stage);
}
```

The existing event API, scheduler infrastructure, and RPC protocol
all support this without modification.

## 4. Risk Assessment

| Risk | Severity | Likelihood | Mitigation |
|------|:--------:|:----------:|-----------|
| Cross-token event reuse in multi-seq | HIGH | LOW (D6 only) | Document as D6 design constraint; double-buffered events |
| Deadlock with n_stages=8 on slow GPU | LOW | LOW | GGML_SCHED_MAX_STAGES=8 guard; n_stages capped at n_backends+1 |
| Pipeline bubble from empty stage | LOW | MEDIUM | Skip empty stages (embed is <0.1% of time) |
| Event leak on early exit | LOW | LOW | ggml_backend_sched_free() already cleans up |

---

## 5. Decision for D5.5 Implementation

Based on the prototype findings:

1. **Use a loop-based state machine** in `llama_decode_gpipe_impl()`.
   Replace the 2-case switch with a `for` loop over `n_stages`.

2. **Keep single-event-per-stage design.** It works correctly for Mode A
   (single sequence). Document the double-buffering requirement for D6.

3. **Topology-aware default.** Set `n_stages = n_backends + 1` at
   `sched_reserve()` time when `GGML_SCHED_GPIPE=1`.

4. **No change to ggml_backend_sched struct.** The existing
   `gpipe_events[8]` array is sufficient.

5. **No change to RPC protocol.** Per-split `GRAPH_COMPUTE` continues
   to work; `GRAPH_COMPUTE_ALL` (Path C) is orthogonal.

## 6. Straggler Isolation Design

Per D5.1, the straggler is `backend[1]` (RPC0 on romulus, ~10 ms).
The pipeline overlap works as follows:

```
Token T:

Sub-stage 0 (embed): 0.01 ms
  → record event[0]

Sub-stage 1 (RPC0): wait event[0], compute 10.0 ms
  → record event[1]
  // RPC0 is slow -- but Token T+1 can start its embed + RPC0
  // while Token T's ROCm0 (stage 2) is still running

Sub-stage 2 (ROCm0 + gather): wait event[1], compute 5.7 ms
  → record event[2] (kv_ready for T+1)

Token T+1 overlaps:
  embed(T+1) during ROCm0(T)
  RPC0(T+1) during ROCm0(T) ... straggler overlap achieved
```

The key insight: **the straggler does NOT block faster backends** because
each backend is a separate pipeline stage. The straggler only blocks its
own stage's slot.
