## 1. Multi-Slot Requirements

### 1.1 What "Multi-Seq" Means for GPipe

In Mode A (single-sequence), one token flows through all pipeline stages before the next token begins. Mode B allows **multiple sequences to occupy different pipeline stages concurrently**:

```
Sequence A: Stage 0 (embed) → Stage 1 (RPC0) → Stage 2 (ROCm0+gather)
Sequence B:          Stage 0 (embed)       → Stage 1 (RPC0)    → Stage 2
```

This is the "microbatch" model: the pipeline fills with work from different sequences rather than waiting for a single sequence to complete all stages.

> **Post-D6.7 note:** The production implementation refined this model. Single-seq
> (active_sequences < 2) now bypasses the pipeline stage machine entirely — it
> computes the full graph once per token via `llama_decode_gpipe_impl`. The
> multi-stage pipeline (Mode B) only activates when 2+ sequences are concurrently
> in flight, using double-buffered events via `llama_decode_gpipe_multi_impl`.
> The hook in `process_ubatch` routes to the correct path automatically.

### 1.2 Server Multi-Slot Architecture

The llama-server (`tools/server/server-context.cpp`) already supports multi-slot serving:

| Feature | Detail |
|---------|--------|
| Slot count | Configurable via `params.n_parallel` (default 4) |
| Slot selection | LRU + prompt-similarity (longest common prefix) |
| Per-slot state | Prompt cache, generation state, streaming trackers |
| Sequence IDs | `llama_seq_id` per slot, managed via KV cache ops |

**Key insight:** The server slot system is orthogonal to GPipe stages. Server slots manage **which sequences exist**; GPipe stages manage **where each sequence is in the pipeline**. We need to bridge these two systems: each active server slot can advance through pipeline stages independently.

### 1.3 Concurrency Target

For romulus dual-GPU (n_backends=2, n_stages=3):

- Minimum: 2 concurrent sequences at different stages
- Stretch: microbatch_size sequences filling all 3 stages
- Throughput expectation: `global_3bk_pct` improvement from pipeline fill (avoiding empty stages)

## 2. KV Cache Interaction with Pipeline Stages

### 2.1 KV Cache Isolation Model

The KV cache (`src/llama-kv-cache.cpp`) already supports **per-sequence cell isolation**:

| Component | Mechanism |
|-----------|-----------|
| Cell ownership | `std::bitset<LLAMA_MAX_SEQ>` per cell tracks which sequences occupy it |
| Slot allocation | `find_slot()` searches for empty or single-occupancy cells |
| Sequence ops | `seq_rm()`, `seq_add()`, `seq_cp()`, `seq_keep()` for full lifecycle |
| Stream mapping | `seq_to_stream` maps sequence IDs to independent cache streams |

**Assessment:** The KV cache isolation model is **already sufficient** for multi-seq GPipe. Different sequences use different cell sets, so sequences at different pipeline stages cannot corrupt each other's KV slots.

### 2.2 Pipeline-Stage-to-KV-Write Interaction

Per ADR-0002, KV writes occur in the **gather stage** (last stage, backend[n-1]). The release condition for token T+1 is: "KV cache write for token T must be complete."

In multi-seq Mode B, this constraint applies **per-sequence**:
- Sequence A's token N+1 cannot start until Sequence A's token N has KV-written
- But Sequence B's token M can advance independently of Sequence A's progress

This means each sequence has its own KV-ready release chain, independent of other sequences.

### 2.3 KV Cache Contention Points

| Contention | Risk | Mitigation |
|-----------|------|-----------|
| Two sequences writing KV simultaneously on same backend | Cell-level race | Already prevented: gather stage is serial per-backend (single device queue) |
| Sequence A reading KV while Sequence B writes | Read-before-write | KV reads are within graph compute; per-backend serialization prevents overlap |
| Slot exhaustion in multi-seq | Cell allocation failure | Existing `find_slot()` handles this; caller retries with backoff |

**Assessment:** No new KV cache conflicts arise from multi-seq GPipe. The existing isolation model handles the per-sequence case correctly.

## 3. Sequencing Constraints

### 3.1 Per-Sequence Constraints (updated post-D6.7)

**Single-seq (Mode A):** Pipeline stages add no throughput benefit for a single data
stream. The production implementation computes the full graph once per token via
`llama_decode_gpipe_impl` and skips the per-stage wait/record state machine. No
per-stage constraints apply.

**Multi-seq (Mode B):** For each individual sequence in multi-seq mode:
- Stage 0 (embed) → Stage 1..n-2 (per-backend compute) → Stage n-1 (gather+KV)
- Token T+1 cannot start Stage 0 until token T completes Stage n-1 (KV-ready release)
- Event signaling enforces ordering: `record[n-1](T)` → `wait[n-1](T)` → `record[0](T+1)`

### 3.2 Cross-Sequence Constraints (new for Mode B)

| Constraint | Rationale |
|-----------|-----------|
| Sequences are **independent** | No ordering between Sequence A and Sequence B's pipeline progress |
| Backend concurrency limit | Each backend can run one graph at a time; sequences share backend queues |
| Stage slot ownership | A stage can hold at most one sequence at a time (single-event-per-stage limitation) |

### 3.3 Scheduling Model Candidates

| Model | Description | Pros | Cons |
|-------|------------|------|------|
| **Round-robin** | Sequences advance in fixed order, one stage per call | Simple; fair | May starve if one sequence is slow |
| **Stage-available** | Any sequence can advance if its target stage is free | Best utilization | Needs per-stage ownership tracking |
| **Slot-based** | Each server slot mapped to a pipeline lane; lanes are independent | Server integration clean | Requires per-slot `gpipe_state` or equivalent |

**Recommendation:** Stage-available or slot-based. Round-robin is too rigid for variable-latency backends (e.g., RPC tail spikes).

## 4. Event Signaling Assessment

### 4.1 Design Limitation (D5.4 Finding 3) — Solved in D6.5-D6.6

The single `gpipe_events[n_stages]` array cannot distinguish between sequences:

```
Sequence A: record[0] → record[1] → record[2]
Sequence B:    record[0] → record[1] → record[2]
```

D6.6 implemented **double-buffered events** (`gpipe_events[2][n_stages]`, banks toggled
per dispatch cycle) as the initial solution. This works for 2 concurrent sequences
(romulus dual-GPU case), verified by live-fire testing.

### 4.2 Mitigation Strategy — Per-Sequence Recommended for Production

After implementation review, the recommended path forward is **per-sequence events**:

| Option | Events | Isolation | Complexity | Profiler Fit |
|--------|--------|-----------|------------|-------------|
| **Double-buffered** (current) | 2 × n_stages | ⚠️ 3+ seqs cause bank reuse | Low | Ambiguous: which seq owns event? |
| **Per-sequence** | n_seqs × n_stages | ✅ Perfect | Low (allocate once) | ✅ 1:1 seq→event mapping |
| **Ring buffer** | M × n_stages (M < n_seqs) | ✅ With correct lifecycle | High (free-list + ref counting) | ⚠️ Need seq→bank mapping |

**Recommendation: Per-sequence.** Event memory is negligible (8 sequences × 5 stages ×
32 bytes = 1.2 KB total). Ring-buffer complexity only pays off at 50+ concurrent
sequences, which is not a realistic GPipe workload. Per-sequence provides perfect
isolation, trivial lifecycle (allocate at setup, free at teardown), and clean
profiler integration (1:1 sequence-to-event mapping for stage timing).

The current double-buffered implementation is functional for 2 sequences and should
be migrated to per-sequence in a follow-up (D6.8+). No urgency — double-buffered
covers the romulus dual-GPU case.

### 4.3 ggml_backend_event API Compatibility

The existing API supports per-sequence events without modification:
- `ggml_backend_event_new(device)` creates an event on the gather backend
- Multiple events can coexist per backend
- The scheduler already supports `events[n_backends][n_copies]` array

The `gpipe_events` array can be expanded from `[MAX_STAGES]` to `[MAX_SEQ][MAX_STAGES]` or `[2][MAX_STAGES]` (double-buffered).

## 5. stage_tokens Vector Assessment

### 5.1 Current Declaration

```cpp
std::vector<llama_seq_id> stage_tokens;  // in llama_gpipe_state
```

**Not yet populated or used.** Size: zero at initialization.

### 5.2 Can It Serve as the Tracking Primitive?

**Yes**, with modifications. The vector can map `stage_index → owning_sequence_id`:

```cpp
// stage_tokens[s] = seq_id currently occupying stage s, or -1 if empty
stage_tokens.resize(n_stages, -1);
```

This provides:
- **Stage ownership:** Which sequence owns which stage
- **Availability check:** `stage_tokens[stage] == -1` means stage is free
- **Advance tracking:** `stage_tokens[stage] = seq_id` when sequence enters stage

### 5.3 Additional Fields Needed (implemented in D6.5)

| Field | Type | Purpose | Status |
|-------|------|---------|--------|
| `seq_stage[seq_id]` | `std::map<llama_seq_id, int>` | Per-sequence current stage position | ✅ Implemented |
| `stage_tokens` | `std::vector<llama_seq_id>` | Per-stage sequence ownership | ✅ Populated by multi-seq dispatch |

The single `cur_stage` int was replaced with per-sequence tracking in D6.5.
`llama_gpipe_multi_seq_setup()` initializes `seq_stage` entries for active sequences.
The dispatch loop in `llama_decode_gpipe_multi_impl` fills `stage_tokens[s]` when
a sequence occupies stage `s`.

## 6. RPC Server Concurrency Model

### 6.1 Current Model

The RPC server (`ggml/src/ggml-rpc/ggml-rpc.cpp`) is **single-threaded per client connection**:
- One client = one thread = sequential request processing
- `wait_compute_idle()` after each request ensures no concurrent graph execution
- Multiple clients get their own threads (but for GPipe, all stages are from the same client)

### 6.2 Multi-Seq Impact

For multi-seq GPipe, the client sends `GRAPH_COMPUTE` requests for different sequences at different stages. The current model handles this correctly:
- The server's compute queue already serializes requests from the same client
- `enqueue_graph_compute()` submits to a `std::deque` with mutex protection
- The compute thread (`submit_compute_job`) processes jobs sequentially

**No server-side changes needed for basic multi-seq dispatch.** The server already accepts and serializes multiple `GRAPH_COMPUTE` requests. The client simply needs to issue them in the correct order (per the pipeline schedule).

### 6.3 GRAPH_COMPUTE_ALL and Profiler Integration

**What GRAPH_COMPUTE_ALL does:** The RPC server deserializes a graph + device list,
creates a multi-device scheduler locally, and calls `ggml_backend_sched_graph_compute()`
synchronously across all GPUs on the endpoint. Returns per-device telemetry
(timing, layer assignments, device metadata).

**Assessment for multi-seq GPipe:**

| Concern | Status |
|---------|--------|
| Direct use for multi-seq dispatch | ❌ Wrong primitive — synchronous across all devices; multi-seq needs per-stage async dispatch with client-managed event sync |
| Profiler heatmap synthesis | ✅ Already built and working — provides per-GPU telemetry for multi-device backends |
| Future: server-side per-stage dispatch | 🔮 A `GRAPH_COMPUTE_STAGE(stage_id)` variant could offload per-stage split filtering to the server; the profiler would get stage-granularity timing |

**Recommendation:** GRAPH_COMPUTE_ALL serves the profiler well and requires no
changes for the current multi-seq implementation. Multi-seq dispatch continues
to use individual `GRAPH_COMPUTE` calls per stage/backend, with the client
managing event synchronization. These are complementary: GRAPH_COMPUTE_ALL for
synchronous multi-device compute + telemetry; individual GRAPH_COMPUTE calls for
async pipeline staging.

## 7. Summary and Recommendations

### 7.1 Feasibility Assessment (updated post-D6.7)

| Concern | Status | Action |
|---------|--------|--------|
| KV cache isolation for multi-seq | ✅ Already solved | Reuse existing `seq_id`-based cell tracking |
| Per-sequence stage tracking | ✅ Implemented (D6.5) | `seq_stage[seq_id]` replaces single `cur_stage` |
| Event signaling ambiguity | ✅ Solved (D6.6) | Double-buffered `gpipe_events[2][n_stages]`; per-sequence recommended for production |
| Server dispatch concurrency | ✅ Already sufficient | Existing queue handles sequential multi-seq |
| `stage_tokens` as tracking vector | ✅ Implemented (D6.5) | Populated with `seq_id` per stage; resized to n_stages |
| Single-seq correctness | ✅ Fixed (post live-fire) | Pipeline bypassed when active_sequences < 2 |

### 7.2 Implemented Approach (post-D6.7)

1. **Track per-sequence stage position:** ✅ `seq_stage[seq_id]` implemented (D6.5)
2. **Double-buffered events:** ✅ `gpipe_events[2][n_stages]` for 2 concurrent sequences (D6.6). Recommend migrating to per-sequence events in follow-up (see §4.2).
3. **Stage ownership via `stage_tokens`:** ✅ Maps stage → seq_id; empty stage = -1 (D6.5)
4. **No server changes for D6.5:** ✅ Client-side dispatch handles multi-seq
5. **KV cache:** ✅ No changes needed; existing isolation sufficient
6. **PRODUCTION REFINEMENT (post live-fire):** ✅ Single-seq bypasses pipeline stage machine; computes graph once per token. Multi-seq (2+ active sequences) uses Mode B with double-buffered events.

### 7.3 Risk Register (updated post-D6.7)

| Risk | Severity | Status |
|------|:--------:|--------|
| Event timestamp overwrite without double-buffering | HIGH | ✅ Mitigated: double-buffered events (D6.6); per-sequence events recommended for 3+ seqs |
| Deadlock if two sequences wait for same stage | MEDIUM | ✅ Mitigated: stage-available scheduling prevents double-claim |
| Throughput regression from event allocation overhead | LOW | ✅ Acceptable: double-buffered adds 1 extra event set; per-sequence adds n_seqs × n_stages (~1KB) |
| Sequence starvation under round-robin | MEDIUM | ✅ Mitigated: stage-available scheduling used; idle stages accept any sequence |
| Single-seq token data mixing across stages | HIGH | ✅ Fixed: production refinement bypasses pipeline for single-seq; computes graph once per token |
