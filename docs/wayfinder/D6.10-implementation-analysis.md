## 1. Problem Summary

### Current state

The multi-seq GPipe dispatch (`llama_decode_gpipe_multi_impl`) calls
`ggml_backend_sched_graph_compute_async` once per pipeline stage, reusing
the same graph. Between stages it currently calls:

```cpp
// src/llama-context.cpp:135-137
if (stage > 0) {
    ggml_backend_sched_synchronize(sched);
}
```

This drains **all backends** unconditionally, serializing GPU work that could
overlap. The original design used `ggml_sched_gpipe_wait_seq()` for per-stage
event signaling, but it is a silent no-op because:

| Cause | Source |
|-------|--------|
| Events created on gather_backend->device (always CPU) | `ggml-backend.cpp:2887-2896` |
| CPU device `event_new` is NULL | `ggml-cpu.cpp:494` |
| `ggml_backend_event_new` returns NULL when iface->event_new is NULL | `ggml-backend.cpp:827-832` |
| All gpipe_events are NULL | — |
| `ggml_sched_gpipe_wait_seq` returns immediately (ev == NULL check) | `ggml-backend.cpp:2938-2939` |

### Backends with event support

| Backend | `event_new` | Source |
|---------|:-----------:|--------|
| CUDA | ✅ | `ggml-cuda.cu:5848` |
| SYCL | ✅ | `ggml-sycl.cpp:5581` |
| Vulkan | ✅ | `ggml-vulkan.cpp:17293` |
| Metal | ✅ | `ggml-metal.cpp:765` |
| WebGPU | ✅ | `ggml-webgpu.cpp:3331` |
| RPC | ✅ | `ggml-rpc.cpp:4430` |
| HIP | ✅ (via CUDA hipify) | — |
| CPU | ❌ NULL | `ggml-cpu.cpp:494` |
| OpenCL | ❌ NULL | `ggml-opencl.cpp:8427` |
| ZenDNN | ❌ NULL | `ggml-zendnn.cpp:646` |

### Romulus topology

Backend order in scheduler: `[ROCm0 (HIP), RPC0 (CUDA/3060Ti), CPU (gather)]`.
Both GPU backends support events; CPU does not.

## 2. Garbling Risk Analysis

### Garbling mechanisms encountered in this codebase

1. **FUSE/NTFS mmap corruption** (`docs/wayfinder/MASTER-ORCHESTRATION-PLAN.md:58`):
   Model files on `/mnt/models` SMB share with hard-link count > 1 return
   silently corrupted data. Workaround: `--mlock`. Not related to event
   signaling but shows garbled output manifests silently — no crash, just
   wrong tokens.

2. **MTP model garbling** (`docs/wayfinder/D4.1-romulus-baseline-analysis.md:212`):
   Combined target+draft GGUF generates garbled output without
   `--spec-type draft-mtp`. Related to dual-context dispatch, not events.

3. **-INFINITY NaN/corruption** (`docs/wayfinder/TRACKING.md:116`):
   CUDA kernel `-INFINITY` literals caused silent NaN on Blackwell sm_120.
   Fixed in C1.1 via `neg_inf_f32()` helpers.

4. **Dual-process GPU memory corruption** (`docs/wayfinder/TRACKING.md:50-53`):
   Client and server accessing same physical GPU caused `RPC_STATUS_ASSERT`
   during cleanup. Deployment constraint, not a code bug.

### D6.10-specific garbling risk: concurrent tensor buffer overwrite

**Root cause**: The multi-seq dispatch reuses the same graph (`gf`) and tensor
buffers across stages. If stage N+1's `graph_compute_async` submits work before
stage N's backends complete, two stages race on shared tensor data.

**ADR-0002 KV ordering**: KV cache writes happen in the **gather split** (final
split, CPU backend on romulus). Token T+1's embed split can only start after
token T's KV writes are committed (`docs/adr/0002-gpipe-kv-ordering.md:60`).

**The risk with GPU-only event waiting**: If we record an event on a GPU
backend (e.g., ROCm0) and wait on it, that guarantees ROCm0's enqueued work is
done. But:
- Other GPU backends (e.g., RPC0) are NOT guaranteed done. However, GPU
  backends use **ordered command streams** — new work submitted to RPC0 in
  stage N+1 executes after stage N's work on the same stream. This is safe.
- The CPU gather backend is NOT guaranteed done. CPU uses a thread pool.
  Without explicit synchronization, stage N+1's CPU work could race with
  stage N's CPU work on shared tensor buffers. **This is the garbling vector.**

**Conclusion**: GPU-only event waiting without CPU synchronization is
**unsafe** — it risks silent output corruption from CPU thread pool races on
KV cache tensors.

### 3.3 `ggml_sched_gpipe_wait_seq`: use event host backend

**File**: `ggml/src/ggml-backend.cpp` (~line 2915)

Replace `gather_bid`/`gather_backend` with `gpipe_event_host_bid`/host backend.
Add fallback: when `event_host_bid < 0` (no GPU backends), synchronize the
full scheduler.

```cpp
void ggml_sched_gpipe_wait_seq(ggml_backend_sched_t sched, int split_id, int seq_id) {
    // ... existing guards ...

    const int host_bid = sched->gpipe_event_host_bid;
    if (host_bid < 0) {
        // No GPU backend with events: fall back to full sync
        ggml_backend_sched_synchronize(sched);
        return;
    }
    ggml_backend_t host_backend = sched->backends[host_bid];
    const int row_off = seq_id * GGML_SCHED_MAX_STAGES;

    if (split_id < 0) {
        for (int s = 0; s < sched->n_gpipe_stages; s++) {
            ggml_backend_event_t ev = sched->gpipe_events[row_off + s];
            if (ev != NULL) {
                ggml_backend_event_wait(host_backend, ev);
            }
        }
    } else {
        if (split_id < sched->n_gpipe_stages) {
            ggml_backend_event_t ev = sched->gpipe_events[row_off + split_id];
            if (ev != NULL) {
                ggml_backend_event_wait(host_backend, ev);
            }
        }
    }
}
```

### 3.5 Multi-seq dispatch: replace full sync with event wait only

**File**: `src/llama-context.cpp` (~line 135)

Replace:
```cpp
if (stage > 0) {
    ggml_backend_sched_synchronize(sched);
}
```

With:
```cpp
if (stage > 0) {
    // D6.10: gate via GPU event — CPU is already drained
    ggml_sched_gpipe_wait_seq(sched, stage - 1, (int)seq_id);
}
```

**Why no CPU sync is needed** (revised 2026-07-16):

| Mechanism | Detail |
|-----------|--------|
| CPU graph_compute is blocking | `ggml_backend_cpu_graph_compute` calls `ggml_graph_compute()` which blocks until the threadpool completes all workers. When `ggml_backend_sched_graph_compute_async` returns, the CPU gather split is **already done**. Source: `ggml-cpu.cpp:170-190`. |
| CPU synchronize is NULL | `ggml_backend_cpu_i.synchronize = NULL` — calling `ggml_backend_synchronize(cpu)` is a no-op. Source: `ggml-cpu.cpp:200-201`. |
| GPU ordered command streams | HIP/CUDA/RPC/Vulkan use FIFO hardware command queues. Stage N+1 work submitted to the same stream executes after stage N work. No race on tensor buffers. |
| The current `ggml_backend_sched_synchronize` already only drains GPU backends | CPU is done before it's called. The replacement GPU event wait achieves the same effect without draining all GPU backends. |

The only backends needing inter-stage gating are GPU backends. The GPU event
recorded on the event host backend signals that backend's stream is drained.
Other GPU streams drain in order when stage N+1 work is submitted. CPU is
already drained by the blocking `ggml_graph_compute` call.

These wrappers call into `*_seq` variants with seq_id=0. No changes needed.

## 7. D6.10.1 — Skip GPU Event Wait for Host→GPU INPUT Copies (2026-07-16)

### Problem

Despite D6.10 shipping GPU event host + copy-slot rotation (n_copies=4), the
`input_copy_slow` phase in Split 2 still spent 3,500 µs per SLOW step blocked on
`ggml_backend_event_synchronize`. Diagnostic with `GGML_SCHED_TRACE=2` revealed
the blocked tensor was `leaf_70` — a 16-byte position ID from CPU to ROCm GPU.

### Root Cause

The `event_synchronize` at `ggml-backend.cpp:2447` gates INPUT tensor copies on
the per-copy-slot GPU event. This ensures the GPU is done with the destination
buffer before overwriting it. With n_copies=1, this is essential — multiple
iterations share the same buffer. With n_copies>1, each iteration uses a
different copy slot, so the event wait is unnecessary for host-sourced tensors
(no GPU→GPU dependency).

The event wait persisted because the copy-slot event, while rotating across
4 slots (n_copies=4), was still being synchronized on each use — even though
the destination buffer was exclusive to the current iteration.

### Fix

In `ggml-backend.cpp:2445-2460`, skip the `event_synchronize` when:
- `n_copies > 1` (copy-slot rotation active)
- Source buffer is on host (`ggml_backend_buffer_is_host`)

```cpp
bool skip_wait = false;
if (sched->n_copies > 1) {
    ggml_backend_buffer_t buf_src = input->view_src ? input->view_src->buffer : input->buffer;
    if (buf_src != nullptr && ggml_backend_buffer_is_host(buf_src)) {
        skip_wait = true;
    }
}
if (!skip_wait) {
    ggml_backend_event_synchronize(sched->events[split_backend_id][sched->cur_copy]);
}
```

### Results (Qwen3.6-35B-MTP, n_gen=32, GPipe stages=3, MTP n_max=2)

| Metric | Before | After | Delta |
|--------|:------:|:-----:|:-----:|
| Split 2 `input_copy_slow` total | 165,000 µs | 2,359 µs | **-98.6%** |
| Total `input_copy_slow` | 172,651 µs | 8,479 µs | **-95.1%** |
| TG TPS | 124.4 | 129.8 | **+4.3%** |
| Wall time (32 tokens) | 257.2 ms | 246.5 ms | **-4.2%** |

### Safety

The fix is safe because:
1. **n_copies>1**: Each iteration uses a different copy slot. No buffer conflict with
   in-flight GPU operations from previous iterations.
2. **Host-source only**: The skipped wait only applies to CPU→GPU copies (position IDs,
   masks, embeddings). GPU→GPU or RPC→GPU copies still synchronize correctly.
3. **12/12 GPipe tests pass**: Zero regressions across the full test suite.
