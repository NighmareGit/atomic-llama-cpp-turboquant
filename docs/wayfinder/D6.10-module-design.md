# D6.10 — Module Design: GPU Event Host for GPipe Multi-Seq

**Date:** 2026-07-16
**Design vocabulary:** [codebase-design SKILL.md](../../../.grok/skills/codebase-design/SKILL.md)

---

## 1. Module Identity

**Module**: GPU event host — the mechanism that detects a GPU-capable backend,
creates GPipe stage events on it, and gates multi-seq stage transitions via
those events instead of a full scheduler drain.

**Seam**: Inside `ggml_backend_sched` (the existing GPipe event infrastructure
at `ggml-backend.cpp:1115-1116`). This is the right seam because:
- Event creation already lives in `ggml_sched_gpipe_init_multi` (same file, line 2874)
- Event wait/record already live in `ggml_sched_gpipe_wait_seq`/`record_seq` (same file, lines 2915, 2955)
- The caller (`llama_decode_gpipe_multi_impl`) already crosses this seam
- No new seam needed — the existing one just gets deeper

---

## 2. Interface

### What callers must know

| Fact | Detail |
|------|--------|
| Function signatures | Unchanged. `init_multi(sched, n_stages, n_seqs)`, `wait_seq(sched, stage_id, seq_id)`, `record_seq(sched, stage_id, seq_id)` |
| Ordering guarantee | After `wait_seq(s, N, q)`, all GPU backends have completed stage N work for sequence q. CPU is already drained (blocking `ggml_graph_compute`). |
| Fallback contract | When no GPU backend supports events (`event_host_bid = -1`), `wait_seq` falls back to `ggml_backend_sched_synchronize`. Callers don't branch on this — same interface, degraded behavior. |
| Invariants | `gpipe_events` must be allocated by `init_multi` before any `wait_seq`/`record_seq` call. `ggml_backend_event_new` may return NULL (CPU, OpenCL) — callers tolerate NULL events. |
| Error modes | None added. Existing `GGML_ASSERT` guards on NULL sched and out-of-range seq_id/stage_id unchanged. |

### What callers do NOT need to know

- Which backend index hosts events (hidden in `gpipe_event_host_bid`)
- Whether events were created on CUDA, HIP, Vulkan, RPC, or CPU (hidden in init)
- Whether the fallback path is active (hidden in `wait_seq`)
- The ordered-stream guarantee (implementation detail of GPU backends)

### Interface size

**One new struct field** (`gpipe_event_host_bid`, `int`) added to `ggml_backend_sched`.
Zero new public functions. Zero new function parameters. The existing three-function
surface is unchanged.

## 3. Implementation (behind the interface)

### 3.1 Struct addition

```cpp
// ggml-backend.cpp, inside struct ggml_backend_sched (~line 1116)
int gpipe_event_host_bid;  // D6.10: GPU backend index hosting gpipe events, -1 if none
```

Default: -1 (uninitialized). Set in `init_multi`, read-only thereafter by `wait_seq`/`record_seq`.

### 3.2 Event host detection (in `init_multi`)

```
for b in [n_backends-1 .. 0]:   // scan from last (gather) to first
    if backends[b]->device->iface.event_new != NULL:
        event_host_bid = b
        break
if no GPU found:
    event_host_bid = -1          // fallback: use gather backend (CPU) — events will be NULL
```

Scan direction: last-to-first. On romulus `[ROCm0, RPC0, CPU]`, this finds RPC0 (index 1).
The gather backend is always at index `n_backends-1`; scanning from there upward finds
the nearest GPU backend.

### 3.3 Event creation (in `init_multi`)

```cpp
ggml_backend_dev_t event_dev = event_host_bid >= 0
    ? sched->backends[event_host_bid]->device
    : sched->backends[gather_bid]->device;
// ... create events on event_dev (was: gather_backend->device)
```

When `event_host_bid >= 0`: events are real GPU events that can be waited on.
When `event_host_bid < 0`: events are NULL (same as current behavior), triggering the fallback.

### 3.4 Event wait (in `wait_seq`)

```cpp
if (event_host_bid < 0) {
    ggml_backend_sched_synchronize(sched);  // fallback: drain everything
    return;
}
ggml_backend_t host = sched->backends[event_host_bid];
// ... wait on host backend's event (was: gather_backend)
```

### 3.5 Event record (in `record_seq`)

```cpp
ggml_backend_event_record(ev, sched->backends[event_host_bid]);
// was: ggml_backend_event_record(ev, sched->backends[gather_bid])
```

### 3.6 Caller change (in `llama_decode_gpipe_multi_impl`)

```cpp
// Before (line 135-137):
if (stage > 0) {
    ggml_backend_sched_synchronize(sched);
}

// After:
if (stage > 0) {
    ggml_sched_gpipe_wait_seq(sched, stage - 1, (int)seq_id);
}
```

That's it. No CPU sync call needed — `ggml_graph_compute()` is blocking.

## 4. Depth Analysis

### Before (current): shallow

```
Interface:  ggml_sched_gpipe_wait_seq(sched, stage_id, seq_id)
            → always a no-op (events are NULL)
Caller:     must call ggml_backend_sched_synchronize(sched) separately
            → caller knows about implementation detail (NULL events)
Result:     full device drain between stages — no overlap
```

The caller (`llama_decode_gpipe_multi_impl`) has to know that events don't work,
and compensate with a different mechanism. **Interface leakage**: the NULL-event
implementation detail is visible at the call site.

### After (proposed): deep

```
Interface:  ggml_sched_gpipe_wait_seq(sched, stage_id, seq_id)
            → gates GPU completion correctly
Caller:     calls wait_seq, no additional synchronization
            → caller doesn't know or care which backend hosts events
Result:     GPU-overlap preserved; CPU implicitly ordered (blocking graph_compute)
```

The caller just calls `wait_seq`. Whether events are on CUDA, HIP, Vulkan, RPC,
or fall back to full sync — the caller doesn't branch on it. **One call site,
all backends covered.**

### Deletion test

If we deleted `gpipe_event_host_bid` and the associated logic, the complexity would
**reappear at the caller**: `llama_decode_gpipe_multi_impl` would again need
`ggml_backend_sched_synchronize(sched)` between stages, losing GPU overlap. The
module earns its keep.

## 5. Alternatives Considered

### Alternative A: Per-backend gpipe_events (rejected)

Create `n_backends * n_stages * n_seqs` events — one per backend, per stage, per seq.
Record on every backend after each stage, wait on all before next stage.

**Rejected because**: Over-engineering. GPU ordered streams make per-backend events
redundant. CPU is already drained. The single event on one GPU backend + the
ordered-stream guarantee is sufficient. Adds allocation complexity and runtime
overhead for zero correctness gain.

### Alternative B: CPU event support (rejected for D6.10 scope)

Add `event_new`/`event_record`/`event_wait`/`event_synchronize` to the CPU backend,
using the existing `n_graph` submission counter as a fence ID.

**Rejected for D6.10**: This is a separate enhancement. The CPU backend's blocking
`ggml_graph_compute` already provides the ordering guarantee needed for D6.10.
Adding CPU events would be a useful follow-up (enables truly async CPU dispatch)
but is out of scope for this fix.

### Alternative C: Event on gather backend with CPU event support (rejected)

Same as Alternative B, but keep events on gather backend. Requires implementing
CPU events first.

**Rejected**: Same reasoning as B — out of scope, and the blocking graph_compute
already handles ordering.

## 6. Test Surface

Tests cross the same seam as callers:

| Test type | What it exercises | Backend config |
|-----------|-------------------|----------------|
| Unit: `test-gpipe-multi-seq-backend` | Fallback path (`event_host_bid = -1`) | CPU-only backends |
| Integration: `test-gpipe-multi-seq-integration` | GPU event path (`event_host_bid >= 0`) | ROCm + RPC + CPU (romulus) |
| Regression: `ctest -R test-gpipe` | All 10 GPipe suites, both paths | Both configs |

The fallback path is trivially tested by the existing CPU-backend unit tests.
The GPU path requires romulus hardware for integration testing — same as all
existing GPipe tests.
