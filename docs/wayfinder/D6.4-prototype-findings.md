1. Can `stage_tokens` vector track sequence ownership per stage?

5. Is KV cache cell isolation compatible with multi-seq?

## 3. Key Findings

### Finding 1: stage_tokens + seq_stage is sufficient for ownership tracking

The `stage_tokens` vector (already declared in `llama_gpipe_state`) maps stage index to owning sequence ID. -1 means free. Combined with `seq_stage` (per-sequence current stage position), this provides everything needed for stage-available scheduling:

```cpp
std::vector<llama_seq_id> stage_tokens;  // stage[s] -> seq_id (-1 = free)
std::map<llama_seq_id, int> seq_stage;   // seq_id -> current stage
```

**Evidence:** Ownership transitions (enter stage, advance, release, wrap) all work correctly in isolation tests.

### Finding 2: Stage release must cascade

When a sequence advances from stage S to stage S+1, stage S must be released (set to -1). Only the last stage (gather+KV) auto-releases. Without cascade release, stages remain occupied and block other sequences:

```
Bug:   stage_tokens[0] stays occupied after seq advances to stage 1
Fix:   stage_tokens[s-1] = -1 when advancing from s-1 to s
```

**Evidence:** The scheduling test initially failed (stage 1 blocked) until cascade release was added.

### Finding 3: Double-buffered event banks are trivially swappable

Two-event-bank toggling (bank 0 / bank 1) is a simple swap operation. Each sequence uses alternating banks per token cycle. No complex pool management needed:

```cpp
int gpipe_event_bank = 0;  // toggle per dispatch cycle
ggml_backend_event_t gpipe_events[2][GGML_SCHED_MAX_STAGES];
```

**Evidence:** The bank toggle test verifies that bank_a and bank_b can be swapped without conflict.

### Finding 4: KV cache isolation model holds for multi-seq

The bitset-based cell ownership model (`cell_owner[c] |= (1ULL << seq_id)`) is inherently per-sequence. As long as different sequences write to disjoint cell ranges (which the existing `find_slot()` guarantees), there is zero cross-sequence KV corruption risk.

**Evidence:** Simulated 1024 cells, two sequences writing to disjoint ranges, 0 conflicts detected.

### Finding 5: Only one sequence can enter stage 0 per dispatch call

Because `seq_stage` is a `std::map` (ordered), the first sequence that matches a free stage gets dispatched. In stage-available scheduling with multiple sequences at stage 0, only one enters per call. The other sequences wait their turn -- this is correct behavior, not a bug.

**Evidence:** The scheduling test shows seq_a entering stage 0 while seq_b waits; seq_b enters when stage 0 is freed.

## 4. Risk Assessment

| Risk | Severity | Likelihood | Mitigation |
|------|:--------:|:----------:|-----------|
| Stage release bug (forgotten cascade) | MEDIUM | MEDIUM | Enforce cascade release in dispatch loop; add assertion: `stage_tokens[old_stage] == seq_id` before release |
| seq_stage map overhead for many sequences | LOW | LOW | For romulus (2 sequences), map overhead is negligible; switch to array if scaling to 32 sequences |
| Event bank mismatch (wrong bank used) | MEDIUM | LOW | Single toggle per dispatch cycle; add assertion: bank in [0, 1] |
| KV cache cell exhaustion with many sequences | LOW | LOW | Existing `find_slot()` with LRU handles this; already tested in llama-server |

---

## 5. Decisions for D6.5 Implementation

Based on the prototype findings:

1. **Use `stage_tokens` + `seq_stage` for ownership tracking.** Replace single `cur_stage` with per-sequence map. Cascade release on stage advance.

2. **Use double-buffered events.** Extend `gpipe_events` to `[2][MAX_STAGES]`. Toggle `gpipe_event_bank` per dispatch cycle.

3. **No KV cache changes needed.** Existing isolation is sufficient. Multi-seq is transparent to the KV layer.

4. **Stage-available scheduling in dispatch loop.** Iterate stages, fill from sequences at matching positions. Preferred over round-robin for fault tolerance.

5. **`microbatch_size` field usage.** Set to 2 for romulus dual-GPU. Guards against over-subscription.
